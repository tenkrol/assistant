# Агент на Финляндии — `@Tenkrol_ag_bot`

Исполнитель задач в Telegram: получает задачу, сам планирует шаги, работает с
файлами и кодом в своей песочнице, делает документы и присылает результат файлом.
Живёт на сервере **Финляндия** (`185.106.94.155`), отдельно от чат-бота в
Испании (`185.174.136.53`): свой токен, свой сервис, своё состояние.

Точка входа проекта — `agent/HANDOFF.md` (передача из сессии чат-бота), ниже —
то, что реально сделано и проверено.

## Как это устроено

```
Telegram ──long poll──► bot.mjs ──► inbox/            (вложения пользователя)
                          │              │
                          │              └─ фото/скан: vision-модель → текст,
                          │                 при неудаче — tesseract (OCR)
                          ├─ buildTaskPrompt()  ──► задача одним текстом
                          │
                          └─ DshTaskRunner ──► dsh --profile headless --json -
                                                  (cwd = workspace, stdin = задача)
                                                        │
                                          workspace/outbox/ + любые новые файлы
                          ┌─────────────────────────────┘
                          ▼
             ответ текстом + файлы (sendDocument/sendPhoto) → Telegram
```

Ключевые решения и почему именно так:

| Решение | Как сделано |
|---|---|
| Рантайм | `@deepseek-ai/dsh@0.2.0-rc.2` из npm, профиль `headless` |
| Модель | провайдер `deepseek-official`, ключ передаётся как `DEEPSEEK_API_KEY`, модель по умолчанию `deepseek-flash` |
| Изоляция | сервисный юнит с `User=agent`, `ProtectSystem=strict`, `ReadWritePaths=/var/lib/agent`, `PrivateTmp`; DSH-песочница `workspace-write` — второй слой |
| Лимиты | 20 минут на задачу, 2 000 000 токенов в сутки, одна задача одновременно |
| Office | LibreOffice 24.2 + `/opt/agent-venv` (python-docx, openpyxl, python-pptx, XlsxWriter, Pillow) |
| Память задачи | `--session-id`: контекст беседы продолжается между задачами, `/new` сбрасывает |
| Картинки | vision-вызов до задачи (`deepseek-flash` видит изображения: ~200 токенов на снимок) + `tesseract` как офлайн-фолбэк |
| Голос | SpeechKit: голосовое сообщение расшифровывается в задачу, ответ на голосовое приходит текстом **и** голосом |
| Ресурсы задачи | свой cgroup на каждый запуск: 1500 МБ, 1.5 CPU, 256 процессов; сервис под `MemoryHigh=1500M`/`MemoryMax=1800M` |

Почему systemd — настоящая граница, а не DSH-песочница: на этом ядре DSH
применяет Landlock в режиме «partial enforcement» и разрешает по политике
временные зоны (`/tmp`). Проверено опытом: запись в `/opt` и `/etc` отклоняется,
запись в `/tmp` — нет. `ProtectSystem=strict` закрывает всё, что за пределами
`/var/lib/agent`, независимо от DSH.

## Файлы: приём и выдача

- Входящие вложения складываются в `workspace/inbox/`; текст из PDF/DOCX/XLSX/
  PPTX/CSV/кода извлекается и попадает в задачу. Фото сохраняется, но
  **содержимое изображения модели недоступно** — это сказано в `AGENTS.md` и в
  ответе пользователю.
- Результат определяется без всякого манифеста (в headless-бандле нет `present`):
  рабочая папка снимается до и после задачи, и каждое появившееся или изменённое
  файл уходит вложением. Приоритет — у `workspace/outbox/`.
- Лимиты: 8 файлов и 45 МБ на файл (Bot API). Файлы сверх лимита остаются на
  сервере, о них сообщается в чат.
- `inbox/` и `outbox/` чистятся от старого по `OUTPUT_RETENTION_DAYS`; черновики
  в корне рабочей папки не удаляются.

## Учёт токенов

`dsh --json` в событии `status/step_end` отдаёт `inputTokens`, `outputTokens`,
`cacheReadTokens`, `cacheWriteTokens`, `totalTokens`. Они суммируются за запуск и
записываются в `state/usage.json` по дню в часовом поясе `TIME_ZONE`. Перед
задачей проверяется дневной лимит; при исчерпании задача не запускается.

## Диалог с задачей: вопросы и варианты

Один запуск DSH — один финальный ответ, поэтому беседа держится на двух маркерах,
которые агент пишет в ответ (правила — в `AGENTS.md` рабочей папки):

- **`ВОПРОС: …`** — данных не хватает. Задача переходит в статус «ждёт ответа»,
  вопрос уходит в чат, сессия DSH сохраняется. Ваш следующий ответ (сообщением
  или реплаем) продолжает **ту же** сессию: агент помнит всё, что уже сделал.
- **`ВАРИАНТ 1: …`, `ВАРИАНТ 2: …`** — путей несколько. Варианты приходят
  **кнопками**; работа не начинается, пока вы не выбрали. Кнопка `✖️ Отменить`
  закрывает задачу.

Поведение задаётся `PROPOSE_VARIANTS` (`auto` — предлагать, только если выбор
меняет результат; `always`; `never`). Ожидание ответа ограничено `AWAIT_REPLY_MS`
(по умолчанию сутки): истёкшие вопросы закрываются со статусом «ответа не
дождалась», файлы остаются в рабочей папке, задачу можно повторить через `/retry`.

## Журнал задач и расход

Каждая задача пишется в `state/tasks.jsonl` (append-only, компакция при старте):
id, статус, время, шаги, токены, файлы, вопрос/варианты, оценка стоимости.
Команды `/tasks`, `/task <id>`, `/retry <id>` читают этот журнал.

Деньги считаются по прайсу DeepSeek с учётом пиковых часов (01:00–04:00 и
06:00–10:00 UTC по будням, в остальное время — половина цены): цены и окна
настраиваются (`PRICE_*`, `PEAK_WINDOWS_UTC`). В сообщении о задаче — точная
оценка по её тарифу; в `/usage` — диапазон «вне пика … пик» по дневным суммам.
Алерты владельцу: пересечение `ALERT_ON_LIMIT_PERCENT` дневного бюджета (один раз
в день), исчерпание лимита, падение задачи при запуске из другого чата.

## Мост: чат-бот в Испании → агент

Схема — **SSH-туннель**, а не Telegram-группа. Группа для этого не годится: Telegram
**не доставляет боту сообщения, отправленные другим ботом**. Проверено на живой группе —
обычное упоминание `@Tenkrol_ag_bot`, ссылка `tg://user?id=…`, явная entity
`{"type":"mention"}` и команда `/help@Tenkrol_ag_bot` до агента не дошли ни разу, тогда как
сообщение владельца в той же группе дошло. Группа остаётся ручным входом для владельца.

Как работает мост:

```
чат-бот (Испания) ──POST /bridge──► 127.0.0.1:8787 ──SSH-туннель──► 127.0.0.1:8787 (агент)
     ▲                                                                    │
     └── пользователю: «задача у агента»          результат и файлы ──► владельцу в личку
```

- Агент слушает **только loopback** (`BRIDGE_BIND=127.0.0.1`, `BRIDGE_PORT=8787`) —
  наружу порт не открывается, TLS не нужен, шифрует SSH.
- Авторизация — bearer-токен (`BRIDGE_TOKEN`), сравнение с постоянным временем; тело
  ограничено 64 КБ, задача — `BRIDGE_MAX_TASK_CHARS`.
- Туннель поднимает Испания: `deploy/setup-bridge-tunnel.sh` создаёт ключ и юнит
  `agent-bridge-tunnel.service` (`ssh -N -L 8787:127.0.0.1:8787`), автоперезапуск.
- Ключ туннеля разрешается на агенте скриптом `deploy/authorize-bridge-key.sh`: он
  ходит **непривилегированным пользователем `agent`** (у него `nologin`) с опциями
  `restrict,port-forwarding,permitopen="127.0.0.1:8787",from="<IP Испании>"`.
  Важно: `restrict` **не запрещает выполнение команд** — это проверено опытом, поэтому
  ключ не должен принадлежать root.
- Задача идёт в общую очередь и подчиняется дневному лимиту; результат агент присылает
  владельцу в личку, а задачи по расписанию и из моста выполняются **в свежей сессии**:
  наследование длинной беседы стоило 130 165 токенов на тривиальную задачу, свежая
  сессия — 7 168 (в 18 раз меньше).

Порядок настройки: на агенте задать `BRIDGE_TOKEN` (`deploy/set-env.sh --stdin`), на
Испании выполнить `setup-bridge-tunnel.sh`, затем на агенте
`authorize-bridge-key.sh "<публичный ключ>"`, и прописать чат-боту
`AGENT_BRIDGE_URL` + `AGENT_BRIDGE_TOKEN`. Без этих двух переменных мост выключен и
поведение чат-бота не меняется.

## Расписания

Агент умеет выполнять задачу по расписанию — DSH-cron в headless-бандле нет, поэтому
планировщик свой (5 полей cron, синтаксис как в Vixie: `*`, `1,3`, `1-5`, `*/15`, `a-b/n`,
имена месяцев и дней недели). Время считается **в вашем часовом поясе**
(`SCHEDULE_TIME_ZONE`, по умолчанию как `TIME_ZONE`), поэтому «по будням в 9:00» — это
9:00 по Москве, а не по UTC.

```text
/schedule add "0 9 * * 1-5" собери сводку по продажам и пришли файлом
/schedule add "*/30 9-19 * * 1-5" проверь входящие и пришли важное
/schedule                                  # список, следующий запуск и счётчик выполнений
/schedule off s3                           # приостановить
/schedule run s3                           # выполнить сейчас
/schedule del s3
```

Что важно в поведении:

- задача идёт в общую очередь и подчиняется дневному лимиту токенов;
- **пропущенные срабатывания не догоняются пачкой**: после простоя выполняется только
  ближайшее, а о пропуске приходит одно сообщение;
- задача по расписанию выполняется без вариантов (варианты нужны живому собеседнику,
  а не будильнику), но вопрос задать может — если без ответа её не решить;
- результат приходит в тот чат, где расписание создано, с пометкой `🕒`.

## Яндекс.Диск: архив файлов

Telegram — хороший канал доставки и плохой архив: файлы уезжают вверх по чату. Поэтому
каждый результат задачи дополнительно уходит на Яндекс.Диск в папку `<YANDEX_DISK_DIR>/<id
задачи>/`, а ежедневный бэкап состояния — в `<YANDEX_DISK_DIR>/backups/` (это офсайт-копия:
Диск и VPS отказывают независимо друг от друга).

```text
YANDEX_DISK=true                 YANDEX_DISK_DIR=/Агент
YANDEX_DISK_MODE=rest|webdav     YANDEX_DISK_PUBLISH=false
YANDEX_DISK_TOKEN=y0_…           YANDEX_DISK_TIMEOUT_MS=60000
# режим webdav: YANDEX_DISK_LOGIN=логин, YANDEX_DISK_PASSWORD=пароль приложения
```

Два способа доступа:

- **`rest`** — OAuth-токен приложения. При создании приложения на oauth.yandex.ru нужно
  **явно выдать доступ к Яндекс.Диску** (`cloud_api:disk.read`, `cloud_api:disk.write`,
  `cloud_api:disk.info`); без этого API отвечает `403 Доступ запрещён` на любой вызов, и
  права задним числом в уже выпущенный токен не добавляются — нужен новый токен.
- **`webdav`** — логин Яндекса и **пароль приложения** (id.yandex.ru → Безопасность →
  Пароли приложений → «Файлы»). Ни приложения, ни прав выбирать не нужно. Публичных ссылок
  в этом режиме нет, квоту Диск через WebDAV не отдаёт — `/disk` честно об этом пишет.

Команды в чате:

- `/disk` — состояние, занятое место и что лежит в папке;
- `/disk get <путь>` — скачать файл с Диска в `inbox/` рабочей папки, чтобы отдать его в задачу;
- `/disk link <путь>` — опубликовать файл и получить ссылку.

Публичные ссылки по умолчанию **не** создаются (`YANDEX_DISK_PUBLISH=false`) и появляются
только по `/disk link`: такая ссылка доступна любому, у кого она есть.

Как получить токен: создать приложение на https://oauth.yandex.ru/client/new с доступом к
Яндекс.Диску (`cloud_api:disk.read`, `cloud_api:disk.write`, `cloud_api:disk.info`), затем
открыть `https://oauth.yandex.ru/authorize?response_type=token&client_id=<id приложения>` и
скопировать токен из адресной строки. Прописать на сервере, не оставляя его в истории команд:

```bash
read -rs DISK_TOKEN && printf '%s' "$DISK_TOKEN" | \
  ssh -i tg-agent/.ssh/tg-agent-deploy root@185.106.94.155 \
  'bash /opt/agent/deploy/set-env.sh YANDEX_DISK=true && bash /opt/agent/deploy/set-env.sh --stdin YANDEX_DISK_TOKEN'
```

Токен Диска **не** передаётся задачам: у них нет доступа к Диску ни через переменные
окружения, ни через файлы — иначе один запущенный агент мог бы вычистить хранилище.

## Быстрый слой, план и память

**Быстрый слой.** Каждый запуск DSH платит за системный промпт и набор инструментов —
около 7 000 токенов и 4–5 секунд даже для «сколько 2+2». Короткий вопрос, которому не нужны
файлы, интернет и программы, отвечает сама модель одним дешёвым вызовом: `ROUTING=auto`
(по умолчанию), `ROUTER_MAX_CHARS=240`. Что попадает в быстрый слой, решает модель по
строгому контракту: ответить или сказать `DSH`. Ошибка быстрого ответа лечится `/retry`
(он всегда идёт в исполнителя), а ошибка `DSH` стоит лишь одного лишнего дешёвого вызова.

**Режим плана.** На большую задачу агент сначала показывает план и ждёт кнопку
«✅ Выполнять»: `PLAN_MODE=auto` (по умолчанию), срабатывает на слова-сигналы (`отчёт`,
`презентация`, `проект`, `исследование`…) или на длинный текст (`PLAN_MIN_CHARS=200`).
План составляется дешёвой моделью, а не отдельным запуском DSH, — это эскиз для
согласования. Задачи по расписанию и из моста план не показывают: утверждать его некому.
Если планировщик недоступен, задача просто выполняется как раньше.

**Память.** Агент ведёт список долговечных фактов о владельце и его делах: инструкции
разрешают ему дописать факт строкой `- факт` в `memory.md` рабочей папки, бот читает файл
после задачи, складывает факты в `state/memory.json` и удаляет файл. Факты подставляются в
каждую задачу блоком «Что уже известно о пользователе» и в быстрый слой. Смотреть —
`/memory`, добавить — `/remember`, убрать — `/forget <номер или часть текста>`. Хранилище
ограничено (120 фактов, 3 000 символов в промпте), поэтому контекст не растёт бесконечно.

## Голос

Входящее голосовое сообщение расшифровывается и попадает в задачу текстом (как и
картинки — модель-исполнитель работает с текстом). Ответ приходит текстом, а голосом —
только если задача пришла голосом (`VOICE_REPLY=auto`; `always` — озвучивать всегда,
`never` — не озвучивать).

Провайдер — Yandex SpeechKit, тот же ключ, что у чат-бота в Испании: он покрывает оба
направления. Речь распознаётся через `stt:recognize` (до ~30 секунд и 1 МБ на запись —
длинная запись честно сообщается как «не удалось распознать», а не теряется), ответ
синтезируется в OGG/Opus `tts:synthesize`, который Telegram играет как голосовое.

```text
STT_PROVIDER=none|yandex|openai      TTS_PROVIDER=none|yandex
STT_API_KEY=…                        TTS_API_KEY=…      # по умолчанию берётся STT-ключ
STT_LANGUAGE=ru-RU                   TTS_VOICE=alena, TTS_SPEED=1.0
STT_MAX_BYTES=1000000                TTS_MAX_CHARS=1200
VOICE_REPLY=auto|always|never
```

Проверено вживую на сервере: синтез фразы «Проверка голосового контура: агент слышит и
говорит» дал 35 КБ OGG/Opus, обратное распознавание вернуло фразу дословно (7 слов из 7).
Ключ SpeechKit перенесён с Испании на Финляндию, не попадая в логи или аргументы команд.

## Ресурсы и устойчивость

Каждая задача запускается в **своём cgroup**: `TASK_MEMORY_MAX_MB` (1500), `TASK_CPU_PERCENT`
(150 = 1.5 ядра), `TASK_PIDS_MAX` (256). Это работает без root и sudo: юнит объявляет
`Delegate=yes` + `DelegateSubgroup=payload`, systemd отдаёт поддерево cgroup сервисному
пользователю, а агент создаёт в нём группу на задачу и кладёт туда процесс dsh.

Проверено на сервере: задача, которой разрешили 64 МБ, была убита ядром **внутри своей
группы** (`CONSTRAINT_MEMCG`, `oom_memcg=…/task-oomtest`), а агент остался жив на том же PID.
Без этого один прожорливый LibreOffice мог забрать всю память и утащить за собой бота.

Две детали, которые легко сломать:

- `ProtectControlGroups=true` монтирует cgroupfs только для чтения и **отключает**
  делегирование (проверено: `EROFS` на `cgroup.subtree_control`) — в юните он выключен
  осознанно, сервис пишет только в своё поддерево;
- если cgroup v2 или делегирование недоступны, агент пишет предупреждение в лог и
  работает без лимитов: отсутствие лимита не должно ломать задачу.

**Бэкап.** `agent-backup.timer` раз в сутки (04:30 + до 5 минут разброса) складывает
`state/`, сессии DSH и рабочий `AGENTS.md` в `/var/lib/agent-backups/agent-<дата>.tar.gz`,
храня последние 7 архивов. Рабочая папка (вложения и черновики) в архив не входит — она
может быть большой, а восстанавливать смысл имеет именно память агента.

```bash
systemctl start agent-backup.service      # сделать бэкап сейчас
systemctl list-timers agent-backup.timer  # когда следующий
tar -tzf /var/lib/agent-backups/agent-*.tar.gz | head
```

**Размер рабочей папки** видно в `/files`, а при превышении `WORKSPACE_ALERT_MB` (2048)
приходит предупреждение владельцу — раз в сутки.

## Ограничения

- Одна задача одновременно: 2 vCPU и ~2 ГБ RAM, LibreOffice берёт ~300 МБ.
- Изображения читаются как текст (vision-модель, затем OCR): исполнитель картинку
  напрямую не «видит», он получает описание и распознанный текст.
- Записи длиннее ~30 секунд распознаются только до этого предела (SpeechKit v1);
  длинная запись честно помечается как нераспознанная.
- Модель разговора — `deepseek-flash` (значение из профиля DSH), менять только
  патчем профиля: env-переменной для модели у DSH нет.
- Сессии DSH лежат в `DSH_HOME/sessions` в zstd-формате и читаются только самим
  DSH; агент считает токены из `--json`, а не из файлов сессий.
- `MemoryDenyWriteExecute` включать нельзя — V8 падает с SIGTRAP.

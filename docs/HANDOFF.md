## ПРИЛОЖЕНИЕ A. Стабильность префикса (про скорость и кеш)

Порядок блоков в системном промпте фиксирован, от неизменного к изменчивому:
1. Роль и правила поведения.
2. Схемы инструментов (тоже часть префикса — любая правка описания инструмента ломает кеш целиком).
3. Описание проекта, конвенции.
4. Только в конце — переменное: дата/время, состояние, алерты, текущая задача.

Требования:
- Не редактировать начало контекста на ходу: ни правила, ни схемы инструментов. Если нужно поменять инструкцию — дописывать в конец, а не править выше.
- Сериализация детерминированная: одинаковые данные дают одинаковый байтовый префикс (стабильный порядок ключей, без случайных id и таймстемпов внутри блока).
- Автосжатие контекста уничтожает кеш и часть договорённостей. Поэтому сессия короткая, а память — в файле, а не в окне.
- Метрики, которые стоит смотреть: токенов на запрос, доля попаданий в кеш префикса, время до первого токена, число неудачных попыток на фичу. Без этих цифр «стало медленно» остаётся ощущением.

**В этом проекте:** порядок соблюдается — сначала роль и схемы инструментов (`src/config.mjs`, список инструментов в `src/bot.mjs`), затем подсказка о возможностях, и только в конце переменное (текущее время, память человека, режим). Описание инструмента правится редко и осознанно: это полный сброс кеша префикса.

## ПРИЛОЖЕНИЕ B. История диалога vs журнал событий

Разделять две разные вещи: **историю переписки** (реплики человека и бота, для контекста разговора) и **журнал событий** (факты о мире: алерты, метрики, состояние сервисов).

Схема события:
- `source` — откуда пришло (сервис, observer, человек);
- `kind` — тип записи: `alert`, `metric`, `info`, `action` (не смешивать тип с источником: это разные поля);
- `id` — идентификатор записи, для дедупа;
- `turn_id` — привязка к реплике диалога (иначе ответы бота теряются при сборке контекста);
- `ts` — время наблюдения;
- `payload` — данные.

Дедуп:
- по `id` — только повторная доставка одного и того же;
- для повторяющихся алертов нужен **семантический ключ** (source + kind + суть события) и агрегация: «алерт повторялся N раз за окно», а не N строк;
- окно дедупа берётся из существующей настройки (`dedup_window_minutes`), а не задаётся заново.

Окно контекста:
- «последние 2 часа» теряют состояние в тихие периоды. Нужен **всегда включаемый снимок состояния** + отдельный блок незакрытых алертов. Плюс ограничение по числу событий, а не только по времени.

Согласование с существующим журналом:
- Если в проекте появится журнал событий, новую схему **не дублировать**: переиспользовать существующие поля и имена, добавить недостающее (`kind`, `turn_id`, семантический ключ) как расширение. Два параллельных журнала с разным дедупом — прямой путь к расходящейся истине.

**В этом проекте:** отдельного журнала событий нет — есть история переписки (`/var/lib/tg-agent/history*.json`), системный журнал (`journalctl`) и файлы состояния. Когда появятся алерты сторожа и метрики моделей, их надо строить по схеме выше; упомянутых `journal_schema.md` и `harness.yaml` здесь нет — это общие принципы, а не текущие файлы.

# tg-agent — ассистент для Telegram, VK, VK Teams и MAX на прямом API модели

Небольшой сервис: бот для Telegram и мессенджера MAX (max.ru), который отвечает
через любой OpenAI-совместимый Chat Completions API (DeepSeek, OpenAI,
OpenRouter, локальный сервер) либо через локальный DSH CLI — см. «Бэкенды
модели». Без зависимостей — только Node 20.6+ и стандартная библиотека.

Умеет: long polling, контекст диалога на каждый чат, команды, напоминания и
память о фактах на пользователя (в группах личные данные не показываются),
город по умолчанию для погоды, утренний дайджест по расписанию, учёт расхода
токенов с дневным лимитом, кнопки под ответом, ограничение доступа по
пользовательскому ID, корректное разбиение длинных ответов, повторные попытки
при 429/5xx, сохранение истории и позиции опроса между перезапусками.

Ядро ассистента одно для обеих платформ, а вся платформенная специфика вынесена
в адаптеры — см. «Архитектура: одно ядро и адаптеры платформ» и «Подключение
MAX».

## Архитектура: одно ядро и адаптеры платформ

Ассистент разделён на **общее ядро** и **адаптеры платформ**.

- **Ядро** (`src/bot.mjs`, класс `Assistant`; исторический алиас
  `TelegramAgentBot`) отвечает за модель и инструменты, историю диалогов, память
  о пользователе, напоминания, утренний дайджест, учёт токенов, доступ и очередь
  сообщений. О мессенджере оно не знает: ядро работает только с нейтральными
  апдейтами и нейтральной клавиатурой.
- **Адаптеры** (`src/platforms/*`) содержат всю платформенную специфику.
  `src/platforms/port.mjs` описывает контракт порта; `src/platforms/telegram.mjs`
  — Telegram (HTML, разбиение по 4096 символов, `reply_markup`, ответ на
  `callback_query`, `typing`); `src/platforms/max.mjs` — MAX (long polling с
  `marker`, `inline_keyboard`, `POST /answers`, `typing_on`).
  `src/platforms/index.mjs` — фабрика `createPlatform(config, logger)`, которая по
  `PLATFORM` лениво подгружает нужный адаптер, и `stateFile(dataDir, base,
  platformName)`, которая выдаёт имя файла состояния для платформы.

Контракт порта (подробности — в комментарии `src/platforms/port.mjs`):
`start`/`stop`, `getUpdates({cursor, timeoutSec})`, `sendText({chatId, markdown,
replyToMessageId, keyboard})`, `editText(...)`, `answerCallback({callbackId, text,
alert})` и `sendTyping({chatId})`. Адаптер приводит апдейт к нейтральному виду:
`kind` (`message` или `callback`), `id`, `chat {id, type}`, `from {id, name,
username, isBot}`, `text`, `addressed` (личка, упоминание бота или ответ ему),
`replyToMessageId`, а для кнопок — `callback {id, data, messageId, text}`.

Клавиатура тоже нейтральная: ядро строит её как
`{ rows: [[{ text: '✖️ Отменить', data: 'cancel:3' }, { text: 'Сайт', url: 'https://…' }]] }`,
а адаптер сам переводит её в свой формат (Telegram `reply_markup`, MAX
`inline_keyboard`) и отбрасывает кнопки, которые платформа не умеет рисовать.

**Один процесс обслуживает одну платформу** — её выбирает `PLATFORM`. Точка
входа `src/index.mjs` строит адаптер (`createPlatform`) и основные хранилища
через `stateFile` (история, напоминания, профили, расход), а имя файла позиции
опроса ядро выводит из имени платформы. Это не только упрощает код, но и
гарантирует, что два процесса не пишут один и тот же файл состояния.

Имена файлов состояния (`stateFile` в `src/platforms/index.mjs`):

| Платформа | Файлы в `DATA_DIR` |
|---|---|
| Telegram | `history.json`, `users.json`, `reminders.json`, `usage.json`, `offset.json` |
| MAX | `history-max.json`, `users-max.json`, `reminders-max.json`, `usage-max.json`, `offset-max.json` |

Telegram сохраняет исторические имена, поэтому данные уже работающего бота не
мигрировали и он продолжает с того же места. MAX получает собственные файлы с
суффиксом `-max`. Поведение и набор команд на обеих платформах одинаковые:
различается только адаптер, а ядро общее.

## Быстрый старт

1. **Токен бота.** В Telegram откройте [@BotFather](https://t.me/BotFather) →
   `/newbot` → имя и username → получите токен вида `123456789:AA...`.
2. **Свой Telegram ID.** Напишите [@userinfobot](https://t.me/userinfobot) — он
   пришлёт `Id`. Либо оставьте бота открытым на минуту и посмотрите в ответе
   «Доступ закрыт. Ваш Telegram ID: …».
3. **Ключ модели** (нужен только при `MODEL_BACKEND=openai`; для `dsh`
   пропустите этот шаг). Возьмите в кабинете провайдера (например, DeepSeek).
4. **Конфигурация.**

   ```sh
   cp .env.example .env
   $EDITOR .env      # TELEGRAM_BOT_TOKEN, MODEL_API_KEY, ALLOWED_USER_IDS
   ```

   `.env` читает сам `src/index.mjs` при старте: без пакета `dotenv` и без флага
   `--env-file`. Файл ищется в рабочем каталоге, имя можно переопределить
   переменной `DOTENV_FILE`. Переменные, заданные явно в окружении, имеют
   приоритет над значениями из `.env`.

5. **Запуск локально** (проверить, что всё живо):

   ```sh
   node src/index.mjs
   ```

   Альтернатива, если файл называется иначе или его нужно указать явно:

   ```sh
   node --env-file=.env src/index.mjs
   ```

   В логе появится `bot started`, а в Telegram бот ответит на `/start`.

## Развёртывание на VPS

### Docker Compose

```sh
scp -r tg-agent user@vps:/opt/tg-agent
ssh user@vps
cd /opt/tg-agent
cp .env.example .env && nano .env
docker compose -f deploy/docker-compose.yml up -d --build
docker compose -f deploy/docker-compose.yml logs -f
```

Состояние (история и offset) лежит в томе `tg-agent-data`, поэтому пересоздание
контейнера его не теряет.

### systemd (без Docker)

```sh
sudo useradd --system --shell /usr/sbin/nologin tgagent
sudo mkdir -p /opt/tg-agent && sudo cp -r tg-agent/* /opt/tg-agent/
cd /opt/tg-agent && sudo cp .env.example .env && sudo nano .env
sudo cp deploy/tg-agent.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now tg-agent
journalctl -u tg-agent -f
```

Домашний каталог пользователю не нужен (`--home` не передаётся). Каталог
состояния `/var/lib/tg-agent` создаёт сам systemd по `StateDirectory=tg-agent`
из юнита — вручную `mkdir /var/lib/tg-agent` делать не нужно. Там же юнит
задаёт `Environment=DATA_DIR=/var/lib/tg-agent`.

Тот же порядок автоматизирован: `sudo bash deploy/deploy-remote.sh` (запускать
на сервере из каталога проекта) ставит файлы в `/opt/tg-agent`, создаёт
сервисного пользователя и каталог состояния, пишет и включает юнит, а на шаге
«6/8 ежедневный бэкап состояния» ставит и включает таймер бэкапа — см. «Бэкап
состояния». На шаге «7/8 сервис MAX (если задан MAX_TOKEN)» тот же скрипт
поднимает второй сервис — для MAX, см. «Подключение MAX».

### Через прокси

Если с сервера `api.telegram.org` недоступен (типично для российских сетей),
укажите прокси и включите его поддержку в fetch:

```sh
HTTPS_PROXY=http://user:pass@proxy.example:3128
NODE_USE_ENV_PROXY=1          # Node 24+; иначе запускайте node --use-env-proxy
```

В compose это `command: ["node", "--use-env-proxy", "src/index.mjs"]`. При старте
бот предупреждает, если переменные прокси заданы, но fetch их игнорирует.

**Запускайте ровно один экземпляр на токен** — два поллера на одном токене
получают ошибку `Conflict: terminated by other getUpdates request`.

## Подключение MAX

Ядро то же самое, отличается только адаптер и юнит systemd.

1. **Создайте бота и возьмите токен.** В «MAX для бизнеса»
   ([business.max.ru](https://business.max.ru)) откройте раздел «Чат-боты» и
   создайте бота — токен доступа выдаётся в его настройках (то же доступно в
   мини-приложении «MAX для бизнеса»).
2. **Пропишите токен** в `.env` на сервере: `MAX_TOKEN=<токен>`. Пока переменная
   пуста, сервис MAX не включается.
3. **Разверните тем же скриптом:**

   ```sh
   sudo bash deploy/deploy-remote.sh
   ```

   Шаг «7/8 сервис MAX (если задан MAX_TOKEN)» сам поставит
   `deploy/max-agent.service`, включит и запустит `max-agent`. Если токена нет,
   шаг ничего не включает и печатает подсказку — добавьте токен и запустите
   скрипт снова.

`max-agent.service` запускает то же ядро (`node src/index.mjs`) с
`PLATFORM=max`. `PLATFORM` задаётся **юнитом**, а не `.env`: systemd применяет
`EnvironmentFile` после `Environment=`, поэтому строка `PLATFORM=` из `.env`
перекрыла бы выбор адаптера (при установке `deploy-remote.sh` вообще удаляет её
из `.env`). В `tg-agent.service` по той же причине стоит
`Environment=PLATFORM=telegram`.

**Важно про токен Telegram.** Даже при `PLATFORM=max` конфигурация по-прежнему
требует `TELEGRAM_BOT_TOKEN` (`requireToken` в `src/config.mjs` вызывается
безусловно), поэтому в `.env` должен оставаться и он, пусть даже Telegram-бот не
используется.

**Сертификат.** API MAX (`platform-api2.max.ru`) отдаёт сертификат, подписанный
корневым сертификатом Минцифры, поэтому в системе должны быть установлены
доверенные корневые сертификаты — иначе любая попытка соединения падает с
ошибкой TLS. Команды установки те же, что в комментарии
`deploy/max-agent.service`:

```sh
curl -fsS -o /usr/local/share/ca-certificates/russian_trusted_root_ca.crt \
  https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt
curl -fsS -o /usr/local/share/ca-certificates/russian_trusted_sub_ca.crt \
  https://gu-st.ru/content/Other/doc/russiantrustedca.pem
update-ca-certificates
```

Если поставить сертификаты в системное хранилище нельзя, адаптер подсказывает
альтернативу — PEM-файл через `NODE_EXTRA_CA_CERTS`.

**Ограничения MAX.**

- Не больше **двух сообщений в секунду** в один чат: адаптер сам сериализует
  отправки в чат (пауза 500 мс), поэтому разбитый на части длинный ответ уходит
  по очереди и не упирается в лимит.
- Одно сообщение — до **4000 символов**: более длинный ответ адаптер разбивает
  сам, аккуратно закрывая и переоткрывая блоки кода.
- Long polling (то, что использует бот) MAX официально считает способом для
  разработки: для production платформа рекомендует Webhook, а для него нужен
  публичный HTTPS-адрес. Бот работает на long polling, потому что такому
  развёртыванию не нужен входящий порт и сертификат.

**Один токен — один поллер.** Не запускайте второй экземпляр MAX-бота с тем же
`MAX_TOKEN`: для каждой платформы должен работать ровно один получатель
обновлений (у Telegram то же правило даёт `Conflict`).

## 24/7 на macOS (launchd)

Чтобы бот поднимался при входе и перезапускался после падения, в проекте есть
LaunchAgent: шаблон `deploy/tg-agent.launchd.plist` и установщик
`tools/install-launchd.mjs`, который подставляет в шаблон пути (`node`, точку
входа `src/index.mjs`, рабочий каталог, файл лога) и загружает агент в
`~/Library/LaunchAgents/com.tg-agent.bot.plist`.

```sh
node tools/install-launchd.mjs          # установить/переустановить и запустить
node tools/install-launchd.mjs --status # состояние: plist, строка launchctl, pid, лог
node tools/install-launchd.mjs --unload # остановить и удалить агент
node tools/install-launchd.mjs --node /путь/к/node   # указать интерпретатор
```

Метка агента — `com.tg-agent.bot`, домен — `gui/$UID`; установщик сам делает
`bootout` старой копии, `bootstrap` (с откатом на `load -w`) и `kickstart -k`.

- `KeepAlive` — перезапускает бота после **любого** выхода; `ThrottleInterval 10`
  не даёт перезапускам идти чаще раза в 10 секунд, поэтому падающий на старте
  процесс не крутится в цикле.
- `RunAtLoad` — поднимает бота при входе в систему, `ProcessType Background` —
  без окна и без приоритета UI.
- `StandardOutPath` и `StandardErrorPath` — `data/bot.log`: весь лог бота (и
  stdout, и stderr) пишется туда же, где он был бы при ручном запуске.

Проверить состояние вручную:

```sh
launchctl print gui/$UID/com.tg-agent.bot
```

**Одновременно должен работать ровно один экземпляр.** Перед установкой агента
убедитесь, что бот не запущен вручную:

```sh
pgrep -fl index.mjs        # пусто — можно ставить агента
```

Два поллера на одном токене получают от Telegram
`Conflict: terminated by other getUpdates request`, и сообщения начинает
обрабатывать то один процесс, то другой. Если бот запущен руками — остановите
его (Ctrl+C или `kill <pid>`) и только потом загружайте агент.

**Путь к `node` при обновлении приложения.** Установщик берёт настоящий бинарник
интерпретатора и пропускает shell-обёртки (файл, начинающийся с `#!`): порядок
поиска — `/opt/homebrew/bin/node`, `/usr/local/bin/node`, затем текущий
`process.execPath`; если ничего не подошло, нужен явный `--node`. На машине без
системного `node` (например, когда Node поставляется вместе с приложением — как
здесь: выбран
`/Users/andryukovy/.dsh/dsh-runtimes/dsh-primary-runtime/dependencies/node/bin/node`)
выбранный путь может измениться после обновления приложения — тогда агент
перестанет стартовать, и его нужно переустановить с новым путём:

```sh
node tools/install-launchd.mjs --node <новый путь к node>
```

Для VPS остаются Docker Compose и systemd — они описаны выше; launchd нужен
только на macOS.

Этим же установщиком ставится внешний сторож: он раз в 30 минут проверяет
сервер снаружи и при проблемах пишет владельцу в Telegram (подробности — в
разделе «Мониторинг (внешний сторож)»):

```sh
node tools/install-launchd.mjs --watchdog
```

Без флага `--watchdog` установщик ставит агент бота; `--status`, `--unload` и
`--node` работают для обоих агентов одинаково.

### Heartbeat: видно ли, что процесс жив

Для 24/7 включите в `.env`:

```sh
HEARTBEAT_MINUTES=60
```

Тогда раз в час в лог пишется одна строка (значение `0`, то есть по умолчанию,
полностью выключает heartbeat):

```
heartbeat {"uptimeSec":3600,"chats":3,"reminders":1,"inFlight":0}
```

`uptimeSec` — секунды с запуска, `chats` — сколько чатов в истории,
`reminders` — сколько напоминаний хранится всего, `inFlight` — сколько сообщений
обрабатывается прямо сейчас. По этим строкам видно, что процесс жив, даже когда
боту никто не пишет; в `data/bot.log` они появляются и при запуске через launchd,
и при обычном `node src/index.mjs`.

## Мониторинг (внешний сторож)

Бот на VPS сам о своей пропаже не сообщит: если с сервера недоступен
`api.telegram.org`, алерт оттуда тоже не уйдёт, а если процесс упал — писать
будет некому. Поэтому в проекте есть внешний сторож `tools/watchdog.mjs`: он
работает на Mac, снаружи сервера, раз в 30 минут делает шесть проверок и при
проблемах пишет владельцу в Telegram.

```sh
node tools/watchdog.mjs            # одна проверка с выводом; при проблемах — алерт
node tools/watchdog.mjs --quiet    # молча при успехе (для launchd)
node tools/watchdog.mjs --status   # только показать факты, ничего не отправлять
node tools/watchdog.mjs --test     # отправить тестовое сообщение и выйти
```

Флага `--list` нет: перечень проверок печатает `--help`.

- **Шесть проверок.** `getMe` отвечает с Mac (значит, алерт дойдёт);
  `systemctl is-active tg-agent` по SSH возвращает `active`; последняя запись
  журнала не старше 95 минут (порог `STALE_MINUTES`, по умолчанию 95; при
  `HEARTBEAT_MINUTES=0` проверка пропускается как неприменимая); за последние
  `ERROR_WINDOW_MINUTES` минут (по умолчанию 20) в журнале нет `polling failed`,
  `Conflict` или `ERROR` (известная безобидная строка `offset save failed`
  игнорируется); на сервере ровно один процесс `src/index.mjs`; корневой раздел
  занят меньше чем на `DISK_PERCENT` (по умолчанию 90%) — иначе файлам состояния
  может не хватить места (см. «Бэкап состояния»).
  Проверка «Один экземпляр» считает **все** процессы `src/index.mjs` на сервере,
  поэтому при одновременной работе `tg-agent` и `max-agent` она ожидаемо видит
  два: сейчас `SERVICE` и порог не настраиваются отдельно под каждую платформу.
- **Код выхода.** 0 — всё хорошо, 1 — есть проблемы; при `--quiet` в лог
  `data/watchdog.log` попадают только сообщения об ошибках, поэтому неудачный
  запуск launchd всё равно виден.
- **Антиспам.** Алерт уходит, когда набор упавших проверок изменился или с
  прошлого алерта прошло больше `ALERT_REPEAT_MINUTES` (по умолчанию 180 минут);
  состояние хранится в `data/watchdog.json` (`lastAlertAt`, `lastAlertKey`).
  Когда после алерта всё восстановилось, приходит одно сообщение «бот снова в
  порядке».
- **Установка.** Тот же установщик, что и у бота, но с флагом `--watchdog`; без
  флага ставится агент бота:

  ```sh
  node tools/install-launchd.mjs --watchdog
  node tools/install-launchd.mjs --watchdog --status
  node tools/install-launchd.mjs --watchdog --unload
  node tools/install-launchd.mjs --watchdog --node /путь/к/node
  ```

  Шаблон агента — `deploy/tg-agent-watchdog.launchd.plist`, метка —
  `com.tg-agent.watchdog`, `StartInterval 1800` (раз в 30 минут) и
  `RunAtLoad=false`: первая проверка происходит на первом тике, не при входе в
  систему. Лог — `data/watchdog.log`, состояние — `data/watchdog.json`.
- **Переменные.** `SERVER` (по умолчанию `root@185.174.136.53`), `KEY` (по
  умолчанию `tg-agent/.ssh/tg-agent-deploy`), `SSH_OPTS`, `SSH_TIMEOUT_MS`
  (20000), `HTTP_TIMEOUT_MS` (15000), `SERVICE` (`tg-agent`), `WATCHDOG_STATE`
  (`data/watchdog.json`), `WATCHDOG_CHAT_ID` (по умолчанию — первый id из
  `ALLOWED_USER_IDS`), `TELEGRAM_API_BASE`, `DISK_PERCENT` (90), а также
  `STALE_MINUTES`, `ERROR_WINDOW_MINUTES`, `ALERT_REPEAT_MINUTES` и
  `HEARTBEAT_MINUTES`.
- **Ловушка с heartbeat.** `HEARTBEAT_MINUTES` сторож читает из `.env` на Mac, а
  строку `heartbeat` в журнал пишет бот на сервере — из своего `.env` или юнита
  systemd. Если значения разойдутся (например, на Mac `60`, а на сервере `0`),
  журнал перестанет обновляться и сторож поднимет ложную тревогу в проверке
  «Журнал свежий». Держите значения одинаковыми.

## Бэкенды модели

Переключаются одной переменной `MODEL_BACKEND`.

- **`openai`** (по умолчанию) — обычный HTTP-запрос к OpenAI-совместимому
  Chat Completions API по `MODEL_BASE_URL`. Нужен `MODEL_API_KEY`; работает
  быстро и подходит для любого провайдера (DeepSeek, OpenAI, OpenRouter,
  локальный сервер).
- **`dsh`** — бот запускает локальный `dsh --profile headless "<запрос>"` и берёт
  ответ из stdout. Ключ не нужен: используется уже выполненный локальный вход
  DSH на этой машине, поэтому DSH должен быть установлен, а `DSH_COMMAND`
  указывает на его исполняемый файл. Медленнее — отдельный процесс на каждое
  сообщение.

В обоих случаях контекст диалога собирает сам бот из своей истории
(`HISTORY_LIMIT`), а не хранит провайдер.

## Интернет: web_search, web_fetch и weather

При `WEB_TOOLS=true` (по умолчанию) модель при бэкенде `openai` получает три
инструмента и вызывает их сама — без команд со стороны пользователя.

- **`web_search`** — нативный поиск DeepSeek. Отдельного search-эндпоинта у
  провайдера нет: используется серверный инструмент `web_search_20250305` в
  Anthropic-совместимом `POST {SEARCH_BASE_URL}/messages`. Один поиск — это
  полный ход модели, поэтому обычно занимает 3–6 секунд и заметно расходует
  токены; `WEB_SEARCH_MAX_USES` ограничивает число поисков внутри одного вызова.
- **`web_fetch`** — обычный GET: из HTML вырезаются скрипты, стили и теги,
  декодируются сущности, лишние пробелы схлопываются, а текст обрезается.
  `WEB_FETCH_MAX_BYTES` задаёт, сколько **байт** страницы прочитать: тело
  читается потоком и загрузка обрывается на этом пределе, поэтому большая
  страница не буферизуется целиком; итоговый ответ всё равно сжимается примерно
  до 3000 символов.
- **`weather`** — текущая погода и прогноз на сегодня и завтра по названию
  города. Основной источник — Open-Meteo: геокодинг
  `geocoding-api.open-meteo.com` и прогноз `api.open-meteo.com`; ключ не нужен,
  коды погоды WMO переводятся на русский. Если город не найден или прогноз не
  ответил, инструмент обращается к резервному источнику wttr.in. В ответе —
  город, местное время наблюдения, температура «сейчас» и ощущаемая, описание,
  влажность, ветер, диапазоны на сегодня и завтра и источник. Если не ответил ни
  один источник, `weather` возвращает модели текст ошибки с требованием не
  выдумывать данные — бот честно скажет, что погоду получить не удалось.
  Отдельный инструмент понадобился потому, что `web_search` отдавал
  закешированные страницы, а прогноз в них был на неверный день.
- Поиск использует тот же `MODEL_API_KEY` (ключ DeepSeek) — отдельных ключей не
  нужно.

Защита: `web_fetch` отказывается обращаться к приватным адресам
(`127.0.0.0/8`, `10/8`, `192.168/16`, `172.16/12`, `169.254/16`, `::1`,
`*.local`, `*.internal`, а также `localhost`, `*.localhost`, `0.0.0.0`,
`fc00::/7` и `fe80::/10`) — иначе модель могла бы дотянуться до локальных
сервисов, включая GUI DSH на `127.0.0.1`. Исключения задаются
`WEB_FETCH_ALLOWED_HOSTS` (например, внутренняя wiki).

Системная инструкция по умолчанию уже требует искать свежие данные, а не
отвечать «нет доступа в интернет»; если нужно вернуть прежнее поведение —
`WEB_TOOLS=false`. При `MODEL_BACKEND=dsh` эти переменные не используются: у
агента свои инструменты.

Как проверить в логе: строка `bot started {…, "webTools":"web_search+web_fetch+weather", "timeZone":"Europe/Moscow", …}`
показывает, какие инструменты выданы модели (`"off"` при `WEB_TOOLS=false`) и
какая зона используется для даты и времени. Вызовы видны как
`tool call {"round":0,"name":"web_search","args":{…}}` (или `"name":"weather"`) на
уровне `info` и следом `model answered {…, "toolCalls":1}`. Если поиск
недоступен для модели, `web_search` возвращает текст ошибки в модель, а не
уронит бота.

## Текущее время в запросе

У модели нет часов: без подсказки она выдумывает дату (в диалоге ответила
«6 июля 2025») и из-за этого путает дни в прогнозе и в новостях. Поэтому в
каждый запрос к модели бот добавляет второе system-сообщение с текущим
моментом — например, «Сейчас: вторник, 6 октября 2026 г. в 00:39
(Europe/Moscow)…» — и просьбой считать эту дату верной.

Сообщение собирается заново на каждый ход и в историю не пишется, поэтому не
устаревает в долгом диалоге. На стоимость это влияет незаметно: одна короткая
строка на запрос. Часовой пояс задаёт `TIME_ZONE` (пусто — системная зона);
значение уходит в `Intl`, поэтому подходит формат вроде `Europe/Moscow`.

## Команды бота

| Команда | Что делает |
|---|---|
| `/start`, `/help` | справка |
| `/new` | очистить контекст диалога (модель для чата сохраняется) |
| `/model` | показать текущую модель |
| `/model <имя>` | сменить модель только для этого чата |
| `/whoami` | показать ваш user id, chat id и тип чата |
| `/reminders` | список ваших напоминаний в этом чате (сортирован по времени) |
| `/cancel <номер>` | отменить своё напоминание по номеру из `/reminders` |
| `/city <город>` | город по умолчанию для погоды; без аргумента — показать, `/city нет` — убрать |
| `/memory` | что бот о вас помнит: город и список фактов в виде `№N: текст` |
| `/forget <номер\|all>` | забыть один факт по номеру или сразу все |
| `/stats` | расход токенов: сегодня и вчера, ваша доля и процент израсходованного дневного лимита |
| `/digest` | прислать утренний дайджест в этот чат прямо сейчас |

В группах бот отвечает только на упоминание (`@username`) или на reply к своему
сообщению — иначе он молчит. В личке отвечает на всё.

Посторонний (не из `ALLOWED_USER_IDS`) в группе, который к боту не обратился —
нет ни упоминания, ни reply, — не получает вообще ничего: бот молчит и только
пишет в лог. В личке посторонний получает сообщение с его ID (`DENY_MESSAGE`).

## Группы: отдельный контекст без личных данных

История у каждого чата своя: личная переписка не попадает в группу, а групповая —
в личку, `/new` очищает контекст только текущего чата.

В группе модель получает **только имена** участников — системную строку вида
«Сейчас пишет Вячеслав. Участники этого чата: … Личные факты и город участников
здесь не показываются — личный контекст остаётся в личных чатах.». Личная сводка
профиля (`summary`) в группу не передаётся: факты собеседника в групповой ответ
не попадают, и в системной строке город не называется. Исключение — погода:
`weather` без названного города подставляет сохранённый город участника, поэтому
спрошенная в группе погода его выдаст (см. «Память о пользователе»).

Сообщения в группе уходят модели с именем автора (`Вячеслав: текст`), поэтому
«меня зовут …» привязывается к правильному человеку, и имена в группах бот
помнит. Имя берётся из факта («его зовут X»), иначе — из публичного имени
Telegram (`first_name` или `username`), которое бот запоминает, когда участник
ему пишет. Без имени строки истории не подписываются.

Команды в группе пишутся с упоминанием бота: `/reminders@имя_бота`.

Если нужен личный контекст — город, факты, — надо писать боту в личку: в группе
он вежливо это предложит (так записано в системной инструкции).

## Напоминания

Поставить напоминание можно двумя путями.

1. **Словами.** Напишите обычной фразой: «напомни через 20 минут выключить
   чайник», «напомни завтра в 9 позвонить маме», «напоминай каждый день в 8
   делать зарядку». Модель сама вызывает инструмент `remind` и показывает
   подтверждение с точным временем.
2. **Командами.** `/reminders` — список **ваших** напоминаний в этом чате,
   `/cancel <номер>` — отменить одно из своих. Номер берётся из списка: если
   там `№3`, отправьте `/cancel 3`. Аргумент — только цифры: `/cancel -1` или
   `/cancel 3 4` вернут подсказку «Укажите номер».

Инструмент `remind` принимает текст (до 500 символов), ровно одно из двух —
`in_minutes` (через сколько минут: от `0.05` до `100000`, то есть от трёх секунд
примерно до 69 суток) или `at` (момент в ISO 8601) — и необязательный `repeat`
(`none`, `daily`, `weekly`). Время в `at` может быть со смещением
(`2026-10-06T09:00:00+03:00`) или без него (`2026-10-07T09:00`) — второе
трактуется в `TIME_ZONE`. Момент в прошлом (больше чем на минуту назад)
отклоняется, и модель просит уточнить дату. Если не указать ни `in_minutes`, ни
`at` (или указать оба), инструмент тоже вернёт ошибку.

- **Хранилище.** `DATA_DIR/reminders.json`; файл пишется атомарно (tmp + rename)
  и читается при старте, поэтому напоминания переживают перезапуск.
  Идентификаторы растут и не переиспользуются.
- **Просроченные.** Если бот был выключен, а срок прошёл, напоминания
  доставляются сразу после старта. Просрочка больше двух интервалов опроса (по
  умолчанию — больше 40 секунд) помечается в тексте: «⏰ (пропущено, пока бот не
  работал) Напоминание: …».
- **Повторы.** После срабатывания `daily`/`weekly` переносятся в будущее: к
  прежнему сроку прибавляются целые сутки (или неделя) до первого момента в
  будущем. Шаг фиксирован в миллисекундах, поэтому в зоне без перехода на летнее
  время местное время не «плывёт»; при переходе возможен сдвиг на час.
- **Владелец.** У каждого напоминания записан владелец (`userId`) — тот, кто его
  попросил. В группе сработавшее напоминание подписано владельцем:
  «⏰ Напоминание для Вячеслава: …»; в личке имя не добавляется. Отсрочка кнопкой
  создаёт новое напоминание с тем же владельцем и повтором.
- **Опрос.** `ReminderScheduler` проверяет срок раз в `REMINDER_CHECK_SEC` секунд
  (по умолчанию 20, диапазон 5–600) — один таймер на все напоминания, а не
  таймер на каждое. Перекрывающиеся проверки пропускаются, а неудачная отправка
  не удаляет напоминание: попытка повторится через интервал. В логе при доставке
  — `reminder delivered {id, chatId, lateMs, repeat}`, при сбое —
  `reminder delivery failed {id, chatId, error}`.
- **Ограничение.** Не больше **50** напоминаний на чат и **50** на пользователя:
  при попытке добавить 51-е инструмент возвращает ошибку
  `too many reminders in this chat` или `too many reminders for this user`.
  Владельцем напоминания записывается пользователь, который его попросил
  (`userId`), поэтому `/reminders` в любом чате показывает только ваши
  напоминания, а `/cancel` отменяет только ваши. Напоминание без владельца
  (старые записи) считается общим для чата и видно всем его участникам.
- **Выключатель.** `REMINDERS=false` — планировщик не запускается, инструмент
  `remind` модели не выдаётся, `/reminders` отвечает «Напоминаний нет», а
  `/cancel` — что такого напоминания нет.

## Память о пользователе

При `MEMORY=true` (по умолчанию) бот помнит долговечные факты о собеседнике,
его город по умолчанию для погоды и его публичное имя Telegram. Профиль
(`DATA_DIR/users.json`) привязан к id пользователя, а не к чату, поэтому
работает одинаково в личке и в группе: `/city`, `/memory` и `/forget` меняют
ваш профиль независимо от того, в каком чате вы их отправили. Это отдельная
память: она не зависит от контекста диалога, переживает `/new` и перезапуск
бота.

- **Как попадают факты.** Модель сама вызывает инструмент `remember`, когда
  пользователь сообщает о себе что-то долговечное — «запомни, меня зовут
  Андрей», «я живу в Казани», «я вегетарианец». Один вызов — один факт; у
  инструмента есть необязательный аргумент `city`, который заодно задаёт город
  по умолчанию.
- **Что видит модель.** Перед каждым ответом в личке в системные сообщения
  добавляется сводка известного: город и пронумерованные факты ровно в том
  виде, что и в `/memory` (`№N: текст`), поэтому модель не переспрашивает уже
  сказанное. В группе эта сводка не передаётся — там модель видит только имена
  участников (см. «Группы»).
- **Хранилище.** `DATA_DIR/users.json` (версия 1). Файл пишется атомарно (tmp +
  rename), как история и напоминания, и читается при старте. Кроме города и
  фактов в профиле лежат публичное имя (`first_name`) и `username` из Telegram.
  Факты нумеруются по пользователю, и номера не переиспользуются: `/forget 2`
  указывает на тот же факт и после удаления соседних.
- **Границы.** Не больше 200 символов на факт и 50 фактов на пользователя;
  повтор (без учёта регистра и лишних пробелов) второй раз не создаётся.
  Профилей хранится не больше `MAX_USERS` (по умолчанию 1000): при переполнении
  первыми вытесняются профили, которые дольше всех не обновлялись.
- **Команды.**
  - `/city <город>` — задать город по умолчанию; `/city` без аргумента —
    показать, `/city нет` — убрать.
  - `/memory` — город и список фактов в виде `№N: текст`.
  - `/forget <номер>` — забыть один факт, `/forget all` — все сразу.
- **Город для погоды.** Если модель вызывает `weather` без города, бот
  подставляет сохранённый: спрашивать «какая погода?» без города достаточно.
  Подстановка не зависит от типа чата, поэтому и в группе погода по
  сохранённому городу участника показывается. Работает это при
  `MODEL_BACKEND=openai` — у бэкенда `dsh` инструменты свои.
- **Выключатель.** `MEMORY=false` — инструмент `remember` модели не выдаётся,
  город для `weather` не подставляется, а `/city`, `/memory` и `/forget`
  отвечают «Память профиля выключена.»

## Утренний дайджест

При `DIGEST=true` (по умолчанию) бот раз в сутки сам присылает в чат короткую
сводку; команда `/digest` присылает её же по запросу, в текущий чат.

- **Когда.** В `DIGEST_TIME` (по умолчанию `08:00`) по локальным часам зоны
  `TIME_ZONE`. Формат — `HH:MM` (`00:00`–`23:59`, проверка шаблоном
  `TIME_PATTERN` в `src/digest.mjs`); значение, которое под него не подходит,
  молча заменяется на `08:00`. Пропущенный запуск не отыгрывается: если в этот
  момент процесс не работал, дайджеста за тот день не будет.
- **Кому.** Список `DIGEST_CHAT_IDS`; если он пуст — всем из
  `ALLOWED_USER_IDS`. При `ALLOW_ALL_USERS=true` и пустом `DIGEST_CHAT_IDS`
  отправлять некому, и в лог попадает предупреждение
  `digest enabled but there is nobody to send it to`.
- **Что внутри.** Приветствие с именем (если в профиле есть факт вида «его зовут
  Имя»), дата, погода по городу из профиля (инструмент `weather`), праздники
  (сегодняшние или ближайший), напоминания **только на сегодня** — время
  `HH:MM`, пометки «(каждый день)» и «(каждую неделю)», а при пустом списке
  «— на сегодня ничего не запланировано», — затем необязательный блок по темам
  `DIGEST_TOPICS` (не больше трёх тем, выдержка из каждой — 400 символов),
  анекдот дня (`DIGEST_JOKE`) и подпись со ссылками на `/reminders` и `/memory`.
  Общая сводка новостей (`DIGEST_NEWS`) по умолчанию выключена и в дайджест не
  попадает.
- **Темы и погода.** Погоду дайджест запрашивает своим вызовом `weather` — он
  работает и при `MODEL_BACKEND=dsh`; блок тем появляется, только если
  `WEB_TOOLS=true` и бэкенд `openai`, потому что собирается через `web_search`.
  При пустых `DIGEST_TOPICS` и выключенной общей сводке новостей поиск вообще
  не выполняется.
- **Сбои.** Ошибка погоды или поиска не мешает отправке: раздел просто
  пропускается, а в лог пишется `digest weather failed` или
  `digest search failed`. Неудача с одним чатом не мешает остальным:
  `digest failed {chatId, error}`.
- **Журнал.** Перед сборкой пишется `digest scheduled {at, chats, topics}` —
  когда следующий запуск и сколько адресатов и тем; при отправке —
  `digest sent {chatId}`. Эти две строки и поле `digest` в `bot started`
  (`08:00 Europe/Moscow` или `off`) показывают, что таймер вообще поставлен.
- **Выключатель.** `DIGEST=false` — таймер не создаётся, `/digest` отвечает
  «Дайджест выключен (`DIGEST=false`).»

## Расход токенов и дневной лимит

Каждое обращение к модели учитывается в `DATA_DIR/usage.json`, а команда
`/stats` показывает счётчики.

- **Что считается.** Запросы (обращения к модели), токены запроса (`prompt`),
  токены ответа (`completion`) и кешированные токены (`cached`) отдельной
  строкой, плюс разбивка по пользователям (`byUser`).
- **День.** Календарный день в зоне `TIME_ZONE`, а не UTC (функция `dayKey`):
  «сегодня» значит то же, что и для читающего. Хранятся последние
  `USAGE_RETENTION_DAYS` дней (по умолчанию 60), старые удаляются при загрузке и
  записи файла.
- **Что показывает `/stats`.** Числа за сегодня (запросы, токены, из них из
  кеша), вашу долю, вчерашний итог за его запросы и — если лимит задан —
  `Лимит: N токенов в день, израсходовано K%`; без лимита строка «Дневной лимит
  не задан (`DAILY_TOKEN_LIMIT=0`)».
- **Дневной лимит.** `DAILY_TOKEN_LIMIT` (0 — выключено) задаёт бюджет в
  токенах на день; в него входят только `prompt` + `completion`, кешированные
  токены не считаются. Проверка идёт **до** обращения к модели: при исчерпании
  бот отвечает «Дневной лимит токенов исчерпан: … До полуночи новые запросы
  отвечать не буду …» и не вызывает модель до следующего дня по `TIME_ZONE`.
- **Полнота учёта.** Записывается каждый вызов модели: все раунды с
  инструментами суммируются в один вызов (`addUsage` в `src/model.mjs`), как и
  принудительный повтор инструмента `remind`, когда модель ответила словами
  вместо вызова. Сбой записи не мешает ответу — он попадает в лог строкой
  `usage accounting failed`. При остановке бота счётчики сбрасываются на диск
  (`flush`), а сам файл пишется атомарно с задержкой около двух секунд, чтобы не
  писать на каждый токен.

## Кнопки под ответом

Чтобы не набирать команды, к сообщениям бота прикреплены inline-кнопки.

- **Новое напоминание.** Под подтверждением, которое вернул инструмент `remind`,
  две кнопки: «⏰ Отложить на 10 минут» (`snooze:10:<id>`) и «✖️ Отменить»
  (`cancel:<id>`).
- **Список `/reminders`.** До восьми кнопок «✖️ Отменить №N» — по одной на
  напоминание; более длинный список остаётся на `/cancel <номер>`.
- **Что происходит при тапе.** Бот отвечает всплывающей подсказкой и
  переписывает сообщение: клавиатура исчезает, а в конец дописывается строка
  результата — «✖️ Отменено: «…»» или «⏰ Отложено до <время>».
- **Отсрочка.** «Отложить» создаёт **новое** напоминание через 10 минут (от
  текущего момента, а не от прежнего срока) и удаляет старое, поэтому `id`
  меняется; повтор (`daily`/`weekly`) и владелец сохраняются, а в строке
  результата добавляется «(дальше — каждый день)» или «(дальше — каждую
  неделю)».
- **Доступ.** Напоминания принадлежат пользователю, а не чату: чужое
  напоминание в группе кнопкой не отменить и не отложить — `/reminders` и
  `/cancel` работают только со своими. Тап пользователя не из
  `ALLOWED_USER_IDS` (при `ALLOW_ALL_USERS=false`) отклоняется всплывающим
  «Нет доступа.» и ничего не меняет.
- Кнопки — часть платформенного API: в Telegram бот запрашивает
  `callback_query` в `allowed_updates`, в MAX получает `message_callback`, а
  нажатие подтверждает через `POST /answers` (всплывающей подсказкой). После
  обновления кода нужен перезапуск сервиса.

## Бэкап состояния

Состояние бота (`history.json`, `offset.json`, `reminders.json`, `users.json`,
`usage.json`, а у MAX — те же имена с суффиксом `-max`) лежит в `DATA_DIR` — у
инструмента бэкапа этот каталог называется `STATE_DIR`. Раз в сутки его
складывают в архив, а архив можно забрать на Mac — тогда потеря VPS не означает
потерю истории, напоминаний и счётчиков расхода.

### На сервере

Установка входит в `deploy/deploy-remote.sh` (шаг «6/8 ежедневный бэкап
состояния»): скрипт создаёт `/var/backups/tg-agent` с владельцем — сервисным
пользователем и правами `0750`, ставит `tg-agent-backup.service` и
`tg-agent-backup.timer`, перезагружает конфигурацию systemd и включает таймер.

```sh
sudo systemctl start tg-agent-backup.service   # сделать бэкап прямо сейчас
systemctl list-timers tg-agent-backup.timer    # когда следующий запуск
systemctl status tg-agent-backup.service       # чем закончился последний
journalctl -u tg-agent-backup.service -n 30 --no-pager
```

- **Таймер.** Ежедневно в 04:00 по часовому поясу сервера; `Persistent=true` —
  пропущенный из-за выключенной машины запуск выполняется после загрузки.
  Точное время: `systemctl show tg-agent-backup.timer -p NextElapseUSecRealtime
  --value`. Если часы сервера идут по UTC, это 04:00 UTC (07:00 по Москве); при
  другом поясе — просто местные 04:00.
- **Инструмент** `tools/backup-state.mjs`:

  ```sh
  node tools/backup-state.mjs                         # архив + удаление старых
  node tools/backup-state.mjs --send                  # ещё и отправить владельцу
  node tools/backup-state.mjs --list                  # что уже лежит в BACKUP_DIR
  node tools/backup-state.mjs --restore <файл>        # показать план
  node tools/backup-state.mjs --restore <файл> --yes  # восстановить
  ```

  В архив `state-YYYY-MM-DD-HHMM.tar.gz` попадают все файлы `*.json` верхнего
  уровня из `STATE_DIR`; имена внутри архива — без пути, поэтому он
  распаковывается прямо в каталог состояния. Хранятся последние `BACKUP_KEEP`
  архивов (по умолчанию 7). `--restore` без `--yes` только печатает план (и
  завершается кодом 1 — это запрос подтверждения, а не ошибка); с `--yes`
  распаковывает архив, предварительно сохранив текущее состояние как
  `pre-restore-<время>.tar.gz`. `--send` отправляет архив владельцу через
  `sendDocument`; неудачная отправка не портит локальный бэкап.
- **Переменные.** `STATE_DIR` (`/var/lib/tg-agent`), `BACKUP_DIR`
  (`/var/backups/tg-agent`), `BACKUP_KEEP` (`7`) и `BACKUP_CHAT_ID` (по
  умолчанию — первый id из `ALLOWED_USER_IDS`). Юнит задаёт `STATE_DIR` и
  `BACKUP_DIR` через `Environment=`, остальное можно прописать в `.env` — юнит
  подхватывает его через `EnvironmentFile`, оттуда же берётся токен для
  `--send`.
- Каталог `/var/backups/tg-agent` создаёт сам юнит (`ExecStartPre`, от root),
  поэтому вручную его готовить не нужно.
- **Обслуживание диска.** Перед бэкапом юнит выполняет
  `ExecStartPre=+/usr/bin/apt-get clean` и
  `ExecStartPre=+/usr/bin/journalctl --vacuum-size=100M`: на маленьком диске
  (4,8 ГБ) кэш пакетов однажды занял около 1,3 ГБ, место кончилось, бот получил
  `ENOSPC` и обнулил `offset.json`. Префикс `+` выполняет эти команды от root
  вне песочницы, тогда как основная команда идёт под непривилегированным
  пользователем. Занятость корневого раздела дополнительно проверяет внешний
  сторож (порог `DISK_PERCENT`, см. «Мониторинг»).

### Забрать архив на Mac

`tools/pull-backup.sh` копирует самый свежий архив с сервера по SSH и хранит
последние `LOCAL_KEEP` архивов (по умолчанию 14):

```sh
bash tools/pull-backup.sh
SERVER=root@example.com KEY=~/.ssh/id_ed25519 bash tools/pull-backup.sh
```

Переменные: `SERVER`, `KEY` (по умолчанию `tg-agent/.ssh/tg-agent-deploy`),
`REMOTE_DIR` (`/var/backups/tg-agent`), `LOCAL_DIR` (по умолчанию
`tg-agent/backups`), `LOCAL_KEEP` (`14`). Пути привязаны к корню проекта, а не к
текущему каталогу, поэтому скрипт работает откуда угодно — в том числе из cron и
launchd.

Расписание на macOS — LaunchAgent. Сохраните как
`~/Library/LaunchAgents/com.tg-agent.pull-backup.plist`, подставив абсолютные
пути, и загрузите его:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key><string>com.tg-agent.pull-backup</string>
  <key>ProgramArguments</key>
  <array>
    <string>/bin/bash</string>
    <string>/абсолютный/путь/к/tg-agent/tools/pull-backup.sh</string>
  </array>
  <key>WorkingDirectory</key><string>/абсолютный/путь/к/tg-agent</string>
  <key>StartCalendarInterval</key>
  <dict><key>Hour</key><integer>9</integer><key>Minute</key><integer>0</integer></dict>
  <key>StandardOutPath</key><string>/tmp/tg-agent-pull-backup.log</string>
  <key>StandardErrorPath</key><string>/tmp/tg-agent-pull-backup.err</string>
</dict>
</plist>
```

```sh
launchctl bootstrap gui/$UID ~/Library/LaunchAgents/com.tg-agent.pull-backup.plist
launchctl kickstart -k gui/$UID/com.tg-agent.pull-backup   # запустить сейчас
```

То же самое через cron (раз в сутки в 09:00):

```cron
0 9 * * * cd /абсолютный/путь/к/tg-agent && bash tools/pull-backup.sh >> backups/pull.log 2>&1
```

## Как это устроено

- **Polling, а не вебхуки.** Не нужен публичный HTTPS-адрес и сертификат.
  Позиция опроса сохраняется в `DATA_DIR/offset.json` (у MAX —
  `offset-max.json`), поэтому после перезапуска старые сообщения не
  обрабатываются повторно.
- **Очередь на чат.** Сообщения одного чата обрабатываются строго по порядку,
  разные чаты — параллельно, но не больше `MAX_CONCURRENT_REQUESTS` ответов
  одновременно.
- **Разметка и длинные ответы — в адаптере.** Telegram-адаптер конвертирует
  ответ модели в HTML (жирный, курсив, код, ссылки, списки, заголовки) с
  экранированием всего остального, режет текст по 4096 символов с
  переоткрытием тегов кода и при отказе Telegram по разметке повторяет тот же
  текст без неё. MAX-адаптер отправляет markdown (с санитизацией под
  документированное подмножество MAX) и режет текст по 4000 символов. Ядро об
  этих различиях не знает: оно отдаёт адаптеру markdown и нейтральную
  клавиатуру.
- **Повторы.** 429 соблюдает `retry_after`, 5xx и сетевые сбои повторяются с
  экспоненциальной задержкой; 4xx (неверный ключ, плохой запрос) не повторяются.
- **История.** Последние `HISTORY_LIMIT` сообщений на чат, окно всегда
  начинается с реплики пользователя. Файл пишется атомарно (tmp + rename).
- **Завершение.** По SIGTERM (и SIGINT) бот отменяет активные запросы к модели,
  дожидается уже начатых ответов не дольше `SHUTDOWN_GRACE_MS` и сохраняет
  историю и позицию опроса на диск.
- **Гарантия доставки — не «как минимум один раз».** При `SIGKILL` или падении
  процесса возможен момент, когда `offset` уже сдвинут, а ответ не отправлен:
  такое сообщение теряется. Обещания повторной обработки нет.

## Безопасность

- Белый список обязателен: без `ALLOWED_USER_IDS` и без явного
  `ALLOW_ALL_USERS=true` бот не стартует.
- Токены и ключ никогда не попадают в лог: логгер вырезает их из всех строк.
- Ошибки конфигурации тоже не печатают значения переменных — только их длину
  (`got a 42-character value`). Поэтому секрет, вставленный не в ту переменную,
  не утечёт в консоль или journald.
- `.env` не коммитьте; в Docker он передаётся через `env_file`, в systemd —
  через `EnvironmentFile` с правами `600`. В репозитории `.gitignore` уже
  перечисляет `.env`, `data/` и логи (`*.log`).
- Бот хранит историю переписки в `DATA_DIR/history.json` (у MAX —
  `history-max.json`) — учитывайте это, если переписка чувствительная. Личные
  данные профиля (имя, город, факты) лежат рядом, в `DATA_DIR/users.json` (у
  MAX — `users-max.json`); в группы они не передаются, но с диска их стоит
  беречь так же, как историю.

## Диагностика

| Симптом | Причина и что делать |
|---|---|
| `configuration error: TELEGRAM_BOT_TOKEN is required` | не заполнен `.env` |
| `configuration error: MODEL_BACKEND must be one of openai, dsh` | опечатка в `MODEL_BACKEND` |
| `configuration error: DSH_COMMAND is required with MODEL_BACKEND=dsh` | задайте путь к исполняемому файлу `dsh` |
| `configuration error: ALLOWED_USER_IDS is empty` | добавьте свой ID или `ALLOW_ALL_USERS=true` |
| Бот никому не отвечает | проверьте `ALLOWED_USER_IDS`: свой ID покажет `/whoami`, либо первый ответ бота «Доступ закрыт…» с вашим ID |
| Бот отвечает, что не имеет доступа к интернету | проверьте `WEB_TOOLS` (должно быть `true`) и `MODEL_BACKEND` (`openai`) и что в логе есть `tool call`; поиск может быть недоступен для модели — тогда `web_search` вернёт текст ошибки в модель, а не уронит бота |
| Бот путает даты или отвечает про «сегодня» не то | проверьте `TIME_ZONE` и что в логе при старте есть фактическая зона: `bot started {…, "timeZone": …}` |
| Напоминание не пришло | проверьте, что в `.env` стоит `REMINDERS=true` и бот запущен: `launchctl print gui/$UID/com.tg-agent.bot` (или `pgrep -fl index.mjs`); в логе должна быть строка `reminder delivered {id, chatId, lateMs, repeat}` — если её нет, срок ещё не наступил или напоминание отменили |
| `telegram getMe failed: Unauthorized` | токен неверный или отозван в BotFather |
| `Conflict: terminated by other getUpdates request` | запущено два экземпляра на одном токене — например, бот, запущенный вручную, и агент launchd: найдите их через `pgrep -fl index.mjs` и оставьте один; агент останавливает `node tools/install-launchd.mjs --unload` |
| `provider rejected the API key (HTTP 401)` | неверный `MODEL_API_KEY` |
| `provider has no such endpoint or model (HTTP 404)` | проверьте `MODEL_BASE_URL` и `MODEL_NAME` |
| `fetch failed` / тайм-ауты к Telegram | `api.telegram.org` недоступен: VPS вне блокировки или прокси + `--use-env-proxy` |
| Бот не отвечает в группе | нет упоминания `@username` или reply на сообщение бота: напишите `@username вопрос` |
| В группе бот не знает мой город или факты | так задумано: личный контекст (город и факты профиля) в системную строку группы не передаётся — личные вопросы задавайте в личке |
| В группе не видно напоминания другого участника | так задумано: напоминания принадлежат пользователю, `/reminders` показывает только ваши, и `/cancel` отменяет только ваши |
| Команда в группе не срабатывает | команды в группе пишутся с упоминанием бота: `/reminders@имя_бота`; без `@имя_бота` сообщение не считается адресованным боту |
| Бот перепутал, кто что сказал | проверьте, что имя участника известно — публичное имя Telegram (`first_name`/`username`) или факт «его зовут …»; без имени строки истории не подписываются |
| `telegram rate limited` | Telegram ограничил частоту, бот сам выждет `retry_after` |
| Кнопки под ответом не реагируют | после обновления кода перезапустите сервис (`systemctl restart tg-agent` или `launchctl kickstart -k gui/$UID/com.tg-agent.bot`) — старый процесс не запрашивает `callback_query` в `allowed_updates` и не умеет обрабатывать тапы; успешный тап виден в логе как `callback handled` |
| Бот не помнит факты | проверьте `MEMORY` в `.env` (должно быть `true`) и перезапустите бота; что именно сохранено, покажет `/memory` |
| Бэкап не приходит | `systemctl status tg-agent-backup.service` и `journalctl -u tg-agent-backup.service -n 30 --no-pager`; если архивов нет — проверьте права на `/var/backups/tg-agent` (владелец — сервисный пользователь, режим `0750`) и что в `STATE_DIR` есть файлы `*.json` (когда бэкапить нечего, архива не будет); если архив создаётся, но не доходит до Telegram — задайте `BACKUP_CHAT_ID` (по умолчанию берётся первый id из `ALLOWED_USER_IDS`) и `TELEGRAM_BOT_TOKEN`; `systemctl list-timers tg-agent-backup.timer` покажет следующий запуск |
| `226/NAMESPACE` в журнале бэкапа | в `ReadWritePaths` юнита указан ещё не созданный каталог: systemd собирает namespace до `ExecStartPre`, поэтому в списке должен стоять **существующий** родитель (`/var/backups`), а сам `/var/backups/tg-agent` создаёт `ExecStartPre=+/usr/bin/install …` — префикс `+` выполняет её от root вне песочницы, тогда как основная команда идёт под непривилегированным пользователем |
| Дайджест не пришёл | проверьте `DIGEST=true` и `DIGEST_TIME` (формат `HH:MM`; неверное значение молча откатывается к `08:00`), строку `digest scheduled {at, chats, topics}` в журнале и `DIGEST_CHAT_IDS` (пусто — рассылка идёт по `ALLOWED_USER_IDS`, но при `ALLOW_ALL_USERS=true` адресатов нет); пропущенный запуск не отыгрывается, а поле `digest` в `bot started` показывает `08:00 Europe/Moscow` или `off` |
| Расход считается по чужому дню | дни считаются в зоне `TIME_ZONE` (функция `dayKey`) — проверьте её значение в `.env` и что оно совпадает у `/stats` и у записи: пусто означает системную зону, а смена зоны «переносит» уже записанные числа в другой день |
| Бот перестал отвечать из-за лимита | задан `DAILY_TOKEN_LIMIT` больше нуля и дневной бюджет исчерпан: бот отказывается отвечать до полуночи по `TIME_ZONE`; сколько уже израсходовано, показывает `/stats`, а `DAILY_TOKEN_LIMIT=0` снимает лимит |
| Сторож молчит или спамит | посмотрите `data/watchdog.json` (когда был последний алерт и какой набор проблем), `WATCHDOG_STATE` (если состояние пишется в другое место), `ALERT_REPEAT_MINUTES` (по умолчанию 180 минут) и `launchctl print gui/$UID/com.tg-agent.watchdog`; если сторож не может отправить алерт — проверьте ключ `tg-agent/.ssh/tg-agent-deploy` (или `KEY`) и `WATCHDOG_CHAT_ID` |
| MAX не отвечает / ошибка сертификата | `platform-api2.max.ru` подписан корневым сертификатом Минцифры: установите корневые сертификаты (`update-ca-certificates`; команды — в комментарии `deploy/max-agent.service`) или укажите PEM-файл через `NODE_EXTRA_CA_CERTS`. Токен и связь проверяются вручную: `curl -sS -H "Authorization: $MAX_TOKEN" https://platform-api2.max.ru/me` — в ответе будут `user_id` и `username` бота |
| Сервис MAX не запущен | `systemctl status max-agent` и `journalctl -u max-agent -n 30 --no-pager`; убедитесь, что `MAX_TOKEN` заполнен в `/opt/tg-agent/.env`, и не задавайте `PLATFORM` в `.env` — платформу выбирает юнит (`Environment=PLATFORM=max`), а `deploy-remote.sh` при установке удаляет строку `PLATFORM=` из `.env` |
| Два процесса на одном токене | для каждой платформы должен работать ровно один поллер: `pgrep -fl index.mjs`, оставьте по одному процессу на `tg-agent` и `max-agent`; лишний экземпляр MAX-бота с тем же `MAX_TOKEN` не запускайте. У Telegram два поллера дают `Conflict: terminated by other getUpdates request` |
| Диск заполнен | `df -h /` показывает 100%: очистите кэш пакетов (`apt-get clean`) и журнал (`journalctl --vacuum-size=100M`), затем перезапустите сервис. В журнале бота об этом говорит `ENOSPC`, а `offset.json` может оказаться обнулённым. Занятость диска заранее проверяет сторож (порог `DISK_PERCENT`, по умолчанию 90%) |

## Обновление на сервере (релизная схема)

Сервер 185.174.136.53 работает по релизной схеме: `/opt/tg-agent` — симлинк на
`/opt/tg-agent-releases/release-<stamp>`. Обновление выполняет инструмент с
проверкой и автоматическим откатом:

```sh
# 1. скопировать новую версию на сервер (без .env, data, .ssh и macOS-мусора ._*)
# 2. на сервере:
cd /tmp/tg-deploy/tg-agent
/usr/local/bin/node tools/deploy-safe.mjs --dry-run    # проверки без переключения
/usr/local/bin/node tools/deploy-safe.mjs --notify     # проверка -> релиз -> health -> (откат)
/usr/local/bin/node tools/deploy-safe.mjs --status     # какой релиз активен
```

**Важно:** `deploy/deploy-remote.sh` после перехода использовать нельзя — rsync
поверх симлинка пишет внутрь активного релиза и ломает неизменяемость.

Если тесты не прошли или сервис не поднялся, инструмент сам возвращает прежний
релиз и присылает алерт в Telegram.

Node на сервере установлен из официального тарбола в `/usr/local/bin/node` —
этот путь прописан в юнитах (`tg-agent.service`, `deploy-verify.service`).

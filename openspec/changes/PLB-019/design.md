# Техническое решение

## Как устроено сейчас
`ProfileStore` хранит список фактов с пределом и нормализацией; домен `profiles` держит тексты,
предел и правила; `/memory` и `/forget <номер>` читают и удаляют.

## Предлагаемое решение
1. Запись памяти — расширенный факт: `id, subjectId, scopeId, kind, value, sourceRef,
   confirmationStatus, validFrom, expiresAt, supersedesId, version`. Хранение — тот же файл
   профиля (миграция на месте), не второй модуль.
2. `src/memory.mjs` (доменный) — операции `list/remember/correct/forget/export`, выбор
   релевантной области для retrieval (`scopeId` + статус + срок), конфликты через `supersedesId`.
3. `tombstones` — отдельный компактный список: `id, scopeId, deletedAt`, без текста; проверяется
   при индексации истории, чтобы удалённое не вернулось.
4. Команды: `/memory` (пагинация, фильтр проекта), `/memory correct <номер> <текст>`,
   `/forget <номер>` с уточнением области, `/memory why` для объяснения источника.
5. Retrieval в промпт: только записи разрешённой области, активные, подтверждённые или явные
   предположения, не истёкшие.

## Влияние
Риск: утечка памяти между областями или возврат удалённого. Поэтому retrieval и индексация идут
через один модуль, tombstone проверяется до включения истории, миграция с копией. Откат —
`deploy-safe` (формат совместим: старые поля читаются, новые добавляются).

## Альтернативы
Отдельный сервис памяти (Letta) — необязательная зависимость и второй источник истины.

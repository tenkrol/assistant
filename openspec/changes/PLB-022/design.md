# Техническое решение

## Как устроено сейчас
- `proactive.mjs` фильтрует напоминания и встречи через `canRead`, задачи (`collectCandidates`,
  источник `gathered.tasks`) — без фильтра; доставка идёт текущему target.
- `memory.mjs` проверяет права только в части путей; `rulesOfProfiles.memoryCommand` вызывает
  `list`/`select` напрямую.
- `profiles.mjs` ищет дубль и заменяемый факт по всему профилю без `scopeId`.

## Предлагаемое решение
1. `memory.mjs`: единая проверка в `createMemory` — `canRead(entry)` в `list/select/export/history`
   и `canWrite(entry)` в `remember/correct/forget/undo`; при неизвестной области — отказ.
2. `profiles.mjs`: дедуп/замена только при совпадении `scopeId` **и** `subjectId`; `supersedesId`
   не связывает разные области; перенос между областями не выполняется `correct`.
3. `proactive.mjs`: нормализация задачи к `{userId, scopeId}` из проверенного источника
   (agentBridge activity), `canRead` в `collectCandidates` и повторная проверка перед `send`
   с письменной причиной отказа в журнале; `userId === undefined` → не общедоступно.
4. Тесты-регрессии на каждое воспроизведение из ревью.

## Влияние
Риск: скрыть данные, к которым доступ есть. Поэтому проверки сосредоточены в общем сервисе, а
тесты покрывают обе стороны (участник видит, чужой — нет). Откат — `deploy-safe`.

## Альтернативы
Проверять в каждой команде — ревью показало, что путь через домен этого не выдерживает.

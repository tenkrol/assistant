# Техническое решение

## Как устроено сейчас
- `tg-agent/src/integrations/agent-bridge/index.mjs` — один `POST <AGENT_BRIDGE_URL>`
  (`/bridge`) с `{task, source}`; ответ `{ok, taskId}`; токен `AGENT_BRIDGE_TOKEN`.
  Инструмент модели — `ask_agent`, задача уходит без маршрута, результата на стороне бота
  никто не ждёт.
- `tg-agent/src/outbox.mjs` — HTTP-приёмник `POST /outbox` с `{text,title}`; доставляет
  текст через `bot.deliverAgentMessage`, истории не хватает файлов, `eventId` и `ack`.
- Конфиг: `agentBridge.url/token`, `outbox.token/port`. Домены `agent-link` в `specs/`
  ещё не было; правила связи живут в коде интеграции.

## Предлагаемое решение

### Домен agent-link
```
tg-agent/src/agent-link/
  index.mjs       сборка домена: постановка, ответ, отмена, ревизия
  contract.mjs    версия контракта, поля запросов, route, лимиты
  pending.mjs     ожидающие вопросы агента по чату (taskId, eventId, сессия)
  events.mjs      правила приёма события: дедуп, доставка, ack, memory_proposal
```
Правила домена не ходят в сеть: транспорт приходит портом из `integrations`.
Зависимости: `core → agent-link → integrations`, `agent-link → storage`, `delivery`
получает готовые данные для сообщения.

### Транспорт
```
tg-agent/src/integrations/agent-bridge/
  index.mjs       createAgentBridge: ask_agent, submitTask, replyTask, cancelTask
  contract.mjs    POST /v1/tasks, /v1/tasks/:id/reply, /cancel, GET /v1/tasks/:id
  files.mjs       POST /v1/files (multipart), GET /v1/files/:id
```
- `AGENT_CONTRACT` (`v2` по умолчанию, `v1` — совместимость): в `v1` остаётся только
  прежний `POST /bridge`.
- `AGENT_BRIDGE_URL` по-прежнему база (`…/bridge` или `http://127.0.0.1:8787`); транспорт
  выводит `/v1/*` из базы, токен — `AGENT_BRIDGE_TOKEN`.
- `requestId` — UUID на каждый запрос, хранится в `pending` до `ack`, чтобы повтор после
  таймаута не создал вторую задачу.
- Вложения: файлы из сообщения (документы/фото) сначала `POST /v1/files`, затем
  `attachments[].fileId` в `/v1/tasks`; лимит `AGENT_FILES_MAX_BYTES`.
- `route` — `{platform, botId, chatId, threadId?, messageId?}` из входящего сообщения; при
  отсутствии маршрута задача считается личной задачей владельца (как раньше).

### Получатель событий
`tg-agent/src/outbox.mjs` расширяется, сохраняя текущий текстовый протокол:
- тело с `eventId` и `contract: 2` — событие v2; иначе — прежний `{text,title}`;
- для v2: проверить токен, `eventId`; если уже обработан — ответить
  `{ok:true, eventId, processed:true, duplicate:true}` и ничего не отправлять;
- пользовательские `result`/`question`: доставить в чат из `route` (fallback — владелец),
  заголовок «Ответ агента», текст обрезается до лимита; файлы из `files[]` скачать
  `GET /v1/files/:id` и отправить документами/фото; вопрос дополнительно запомнить в
  `pending` для ответа;
- `memory_proposal`: не создавать сообщение; передать домену памяти ассистента (владелец
  личных фактов), записать факт или отклонить; ответить `ack`;
- после успешной доставки — `{ok:true, eventId, processed:true}`; ошибка доставки — `5xx`,
  агент повторит с тем же `eventId`; журнал дедупликации обновляется только после успеха.

### Дедупликация и ожидающие вопросы
- `tg-agent/src/storage/agent-events.mjs` — JSONL/JSON с атомарной записью:
  `{eventId, taskId, type, processedAt, messageId}`, срок `AGENT_EVENTS_RETENTION_DAYS`,
  компакция при старте. Файл переживает перезапуск; битый файл откладывается.
- `pending` — в существующем состоянии/истории чата: `{chatId, taskId, question, askedAt,
  sessionId?}`. Ответ владельца обычным сообщением: если есть ожидающий вопрос, он
  отправляется `POST /v1/tasks/:id/reply` с новым `requestId`, затем `pending` очищается.
  Просроченный вопрос (срок `AGENT_ANSWER_TIMEOUT_MS`) снимается с сообщением владельцу.
- `ask_agent` в модели сохраняет прежнее поведение: передаёт задачу, говорит владельцу,
  что результат придёт отдельным сообщением; при v2 добавляет маршрут и `requestId`.

### Ревизия и отмена
- Ревизия: инструмент `ask_agent` принимает необязательный `revisionOf` (id прошлой задачи
  из контекста); постановка идёт `POST /v1/tasks` с `revisionOf`, ответ приходит туда же.
- Отмена: `/cancel` для ожидающего вопроса или задачи агента вызывает
  `POST /v1/tasks/:id/cancel` с `requestId`; состояние отмены отдельным сообщением не
  дублируется (его видно в ответе агента).
- Ручной повтор доставки не нужен: `ack` и повторы на стороне агента; бот только
  дедуплицирует.

### Доставка
`delivery` получает от `agent-link` готовый текст и список файлов; оформление — заголовок
«Ответ агента», обрезка по лимиту платформы, файлы после текста. Вопрос оформляется как
вопрос с подсказкой «Ответьте сообщением». `memory_proposal` не проходит через delivery.

### Конфиг
Новые ключи (все с умолчаниями, старый env работает):
`AGENT_CONTRACT` (`v2`|`v1`, по умолчанию `v2`), `AGENT_FILES_MAX_BYTES` (20 МиБ),
`AGENT_EVENTS_RETENTION_DAYS` (30), `AGENT_ANSWER_TIMEOUT_MS` (86 400 000).
Существующие `AGENT_BRIDGE_URL`, `AGENT_BRIDGE_TOKEN`, `OUTBOX`, `OUTBOX_TOKEN` не меняют
смысл. Значения секретов не логируются.

### Совместимость и порядок выката
1. Бот обновляется первым: принимает и старый текст, и события v2; при `AGENT_CONTRACT=v1`
   работает по-старому.
2. Агент уже обновлён (PLA-14) и принимает v2.
3. Откат бота — `deploy-safe` на предыдущий релиз; журнал событий остаётся, повторная
   обработка старых `eventId` не создаёт сообщений.

### Миграция и откат
- Новые файлы состояния создаются пустыми; история чатов не меняется.
- Ожидающие вопросы при рестарте читаются из состояния; просроченные снимаются.
- Откат: предыдущий релиз бота; новые ключи игнорируются, `/outbox` текстовый работает.

## Влияние
- Меняются `tg-agent/src/agent-bridge.mjs` (реэкспорт), `integrations/agent-bridge/*`,
  `outbox.mjs`, `bot.mjs` (ответ на вопрос/файлы), `config.mjs`, тесты, `.env.example`.
- Риск: неверный маршрут доставит результат не в тот чат — закрывается проверкой `route`
  (только настроенный владелец/платформа) и тестами.
- Риск: файлы занимают память — лимит размера, потоковая отправка, без base64 в JSON.
- Риск: дубль сообщения при сбое после отправки — журнал обновляется после успеха, но
  абсолютной гарантии нет; это фиксируется в README.

## Альтернативы
- Оставить только `/bridge` и текст — не даёт уточнений, файлов и дедупликации; отвергнуто.
- Принимать base64 в JSON — ломает лимит и память; отвергнуто в пользу `/v1/files`.
- Хранить `eventId` только в памяти — после рестарта повтор создаст дубль; отвергнуто.
- Отдельный broker/Redis — ноль зависимостей и лишняя инфраструктура; отвергнуто.

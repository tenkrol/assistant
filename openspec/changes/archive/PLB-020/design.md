# Техническое решение

## Как устроено сейчас
`deliverDigest` и напоминания в `bot.mjs`/`core/*`, тихие часы в домене напоминаний, события и
поручения — в своих хранилищах. Единого бюджета и дедупликации нет.

## Предлагаемое решение
1. `src/proactive.mjs` (доменный) — сбор кандидатов из существующих источников (напоминания,
   события, поручения), приоритет по коду, объединение одинаковых событий по ключу.
2. `proactive.json`: `watermark`, `sentToday{counter,date}`, `items[{key,type,plannedAt,expiresAt,state}]`,
   `settings{tz,reviewAt,quiet,channels,categories,dayLimit=3}` — в общем слое хранения, миграция
   с копией, идемпотентная.
3. Один планировщик (расширение существующего таймера, без второго): раз в минуту считает
   кандидатов, проверяет тихие часы по IANA (`Intl.DateTimeFormat`), бюджет, доступ и TTL,
   отправляет и пишет состояние.
4. Кнопки «открыть/выполнено/отложить/отключить тип» — в клавиатуре уведомления; отложенное
   перепроверяется по состоянию объекта.
5. После простоя — не больше одного актуального обзора; просроченные по TTL отбрасываются.
6. Ошибки доставки — backoff по существующей очереди; повтор возможен, exactly-once не обещаем.

## Влияние
Риск: лишние сообщения или дубли. Поэтому бюджет и ключ события проверяются до отправки, а
dry-run режим пишет решения в журнал без отправки. Откат — `deploy-safe`, флаг
`PROACTIVE_ENABLED`.

## Альтернативы
Отдельный планировщик — второй источник истины; BP-04 прямо запрещает.

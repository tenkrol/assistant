# Техническое решение

## Как устроено сейчас
`proactive.json`: `watermark`, `sentToday`, `items[]`, `settings` — на файл/бота; сервис
перебирает targets, но состояние пишет одно.

## Предлагаемое решение
1. Ключ состояния — `principal` (проверенный `userId` + канал). `proactive.json` schema 2:
   `users: { "<channel>:<userId>": { settings, sentToday, watermark, items: {...} } }`.
2. Настройки по умолчанию применяются при первом обращении. Mute и категории — в настройках
   пользователя, не в общих.
3. `items` — по объекту (ключ события), состояние доставки — `deliveries: { "<principal>": state }`,
   чтобы общий объект ушёл каждому ровно один раз.
4. Тик перебирает getargets: для каждого — свои кандидаты (ACL уже есть), свой бюджет,
   свой watermark, свой журнал решения. `skipReview` одного не трогает другого.
5. Миграция: старые общие `settings/sentToday/watermark` переносятся владельцу, копия `.bak`,
   идемпотентность; новые получатели — defaults.
6. Флаг `PROACTIVE_ENABLED` остаётся общим выключателем, включение — в настройках пользователя.

## Влияние
Риск: потерять чьё-то состояние при миграции. Поэтому копия и тест на двух пользователей
(каждому свой обзор, пустой первого не подавляет второго). Откат — `deploy-safe`.

## Альтернативы
Отдельный файл на пользователя — больше файлов, но допустимо; выбрана схема с `users` в одном
файле ради атомарной записи.

# Техническое решение

## Как устроено сейчас
- `history.mjs` пишет по ключу `chatId` без проверки; `NaN` попал в файл.
- `telegram.mjs` на `getUpdates` делает один повтор (`attempt:1`) и продолжает цикл — без
  нарастающей паузы и без уведомления.
- `proactive.mjs` уже умеет `setEnabled`, `settingsFor`, `setReviewAt` для principal; команды нет.

## Предлагаемое решение
1. `history.mjs`: в `add`/`append` проверить `Number.isFinite(Number(chatId))`; при провале —
   `logger.warn('history write skipped: invalid chatId')` и выход без записи.
2. `telegram.mjs`: счётчик подряд идущих ошибок; паузы 1→2→5→15→30 с; на 3-й ошибке одно
   уведомление владельцу (`agent-notify` или `send` в чат владельца); на первом успехе —
   «связь восстановлена», счётчик сбрасывается.
3. `core/commands.mjs`: `/proactive`, `/proactive вкл|выкл`, `/proactive обзор HH:MM`,
   `/proactive тихие HH:MM-HH:MM`; все операции через `proactive.mjs` для текущего principal.
4. Тесты: история с `NaN`/`undefined`; поллинг с подставным fetch (серия ошибок → паузы и
   уведомление, затем успех → восстановление); команды `/proactive` на двух получателях.

## Влияние
Риск: лишние уведомления о связи. Поэтому один алерт на серию и один на восстановление.
Откат — `deploy-safe`.

## Альтернативы
Внешний мониторинг сети — лишняя инфраструктура.

# Техническое решение

## Как устроено сейчас

Miniapp проверяет только общий allow-list. `MobileMediaStore.read` и callback
задач агента не получают владельца объекта. v2-клиент передаёт маршрут ответа,
но не principal автора. Бинарные fetch не используют единый auth-заголовок.

## Предлагаемое решение

`MobileMediaStore.read` становится deny-by-default и требует `userId`. Miniapp
передаёт текущий principal в медиа и callbacks агента; кэш статуса разделяется
по пользователям. Adapter в `index.mjs` фильтрует активность и проверяет владельца
деталей/отмены по данным агента, а исходный текст ищет только в нужном чате.

Контракт v2 получает `principal.userId/scopeId`. Telegram WebApp формирует его из
проверенного контекста инструмента. После валидного initData `/api/auth/session`
выдаёт короткую подписанную cookie для обычных URL ресурсов; ручные fetch также
передают заголовок initData.

`deploy-remote.sh` генерирует unit `deploy-verify` с найденным `NODE_BIN` и
включает timer. Внешние YouTube-fetch ограничиваются `AbortSignal.timeout`.

## Влияние

Старые клиенты v2 без principal продолжают работать и получают прежнего
системного владельца; новые задачи получают точного владельца. Старые записи без
владельца не показываются другому пользователю. Откат — штатный deploy-safe.

## Альтернативы

Передавать initData в query string отвергнуто: секрет оказался бы в URL и логах.
Проверять ownership только в браузере отвергнуто: это не граница безопасности.

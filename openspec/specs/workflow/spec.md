# Спека домена workflow

Правила самого процесса разработки: как оформляются изменения, как проверяется структура, где живут секреты и на каком языке пишутся спеки.

## ADDED Requirements

### Requirement: Изменение оформляется папкой change
Любое изменение поведения системы ДОЛЖНО иметь папку `openspec/changes/PLB-<номер>/`
с `proposal.md`, `tasks.md` и дельта-спекой в `specs/<домен>/spec.md`. Имя папки — только
маска `PLB-<трёхзначный номер>`; номер уникален и берётся по порядку создания.

#### Scenario: Новая фича
- GIVEN в репозитории нет папки изменения для задачи
- WHEN агент или человек начинает менять поведение
- THEN создаётся папка `PLB-<номер>` со следующим свободным номером
- AND название изменения пишется в `proposal.md`, а не в имени папки

#### Scenario: Правка без изменения поведения
- GIVEN изменение — опечатка или форматирование
- WHEN оно коммитится
- THEN в сообщении коммита стоит пометка «без change»
- AND папка изменения не создаётся

### Requirement: Номер изменения не переиспользуется
Номер `PLB-NNN` ДОЛЖЕН быть уникальным навсегда: даже если изменение отменено, его номер
не занимается заново.

#### Scenario: Отменённое изменение
- GIVEN изменение PLB-012 отменили
- WHEN создаётся следующее изменение
- THEN оно получает PLB-013, а не PLB-012

## MODIFIED Requirements

### Requirement: У продукта есть каталог сценариев приёмки
Каталог `docs/acceptance/scenarios.json` ДОЛЖЕН содержать 30 сценариев исходной BP-07; у каждого —
`id`, `bp`, `area`, `level` (unit|contract|integration|live), шаги, ожидаемый результат,
доказательство и статус прогона (`not-run|passed|failed|blocked|skipped`) с датой и SHA.

#### Scenario: Сценарий без уровня
- GIVEN сценарий добавлен без `level`
- WHEN запускается `acceptance.mjs --check`
- THEN проверка падает
- AND деплой не проходит

## ADDED Requirements

### Requirement: Приёмка исполняемая
Раннер ДОЛЖЕН запускать автоматизируемые сценарии (unit/contract/integration) и честно помечать
live как не выполненные до реальной проверки; `skipped` и `blocked` НЕ считаются успехом.

#### Scenario: Запуск приёмки
- GIVEN сценарии с уровнями
- WHEN выполняется `acceptance.mjs --run`
- THEN отчёт содержит по каждому сценарию статус, дату, SHA и доказательство
- AND итоговая строка считает отдельно passed/failed/blocked/skipped/not-run

#### Scenario: Модульные тесты не выдают за live
- GIVEN сценарий уровня live
- WHEN он не выполнялся с настоящим ботом
- THEN его статус не может быть `passed`
- AND матрица показывает его как ожидающий живой проверки

### Requirement: Честная матрица готовности
В репозитории ДОЛЖНА быть матрица `docs/ACCEPTANCE-MATRIX.md` по BP-01…BP-07 с четырьмя
отдельными статусами (код готов / проверено тестами / установлено в проде / принято живым
сценарием), со ссылками на SHA и отчёты.

#### Scenario: Статусы не смешиваются
- GIVEN код задеплоен, но живого сценария не было
- WHEN читается матрица
- THEN «установлено» отмечено, «принято» — нет
- AND видно, какой сценарий остался

### Requirement: Структура проверяется автоматически
`bash tg-agent/tools/spec-check.sh` ДОЛЖЕН находить папки изменений без proposal, tasks
или дельты, имена не в формате `ГГГГ-ММ-ДД-<слаг>` и дельты без требований.

#### Scenario: Неполное изменение
- GIVEN в `changes/` лежит папка без `tasks.md`
- WHEN запускается `spec-check`
- THEN команда завершается с ненулевым кодом
- AND перечисляет, чего не хватает

### Requirement: Секреты хранятся только в шифрованном виде
Значения ключей НЕ ДОЛЖНЫ попадать в репозиторий открытым текстом. Источник — `secrets/prod.env.enc`,
пароль хранится вне репозитория.

#### Scenario: Новая машина
- GIVEN репозиторий склонирован на новую машину
- WHEN выполняется `bash tg-agent/tools/secrets.sh decrypt`
- THEN появляется `.env` с правами 600
- AND без пароля расшифровка невозможна

### Requirement: Спеки и комментарии на русском
Требования, сценарии, документация и комментарии в коде пишутся по-русски.

#### Scenario: Новая спека
- GIVEN агент пишет дельту-спеку
- WHEN он формулирует требование
- THEN текст на русском, формат «ДОЛЖЕН» + сценарий GIVEN/WHEN/THEN

## ADDED Requirements

### Requirement: У продукта есть каталог сценариев приёмки
В репозитории ДОЛЖЕН быть каталог `docs/acceptance/scenarios.json`, где каждый сценарий
описывает пользовательскую задачу, шаги, ожидаемый результат, способ доказательства и статус.

#### Scenario: Сценарий без доказательства
- GIVEN в каталог добавили сценарий без поля `evidence`
- WHEN запускается `node tg-agent/tools/acceptance.mjs --check`
- THEN проверка падает и называет сценарий
- AND деплой не проходит

#### Scenario: Сводка по статусам
- GIVEN каталог заполнен
- WHEN запускается `acceptance.mjs --list`
- THEN печатается количество сценариев по статусам (готово, частично, не реализовано)
- AND видно, какие пункты ещё не доказаны

### Requirement: Фича считается сделанной по сценарию
Новая продуктовая возможность ДОЛЖНА добавлять или обновлять сценарий приёмки в том же
изменении; статус «готово» ставится только после фактического прогона сценария.

#### Scenario: Закрытие изменения
- GIVEN изменение добавляет пользовательскую возможность
- WHEN оно закрывается
- THEN в каталоге есть сценарий с этим поведением
- AND в `tasks.md` указано, как он проверен

Спека домена core

Ядро — конвейер обработки сообщения с неизменным публичным API; команды разбирает отдельный маршрутизатор.


## ADDED Requirements

### Requirement: Публичный API ядра не меняется
Разделение ядра на части ДОЛЖНО сохранить публичные методы и события бота: тот же модуль,
те же имена, параметры и результаты.

#### Scenario: Тесты и вызывающий код
- GIVEN код вне ядра использует публичные методы бота
- WHEN ядро разделено
- THEN импорты и вызовы не меняются
- AND существующие тесты проходят без правок

### Requirement: Обработка сообщения — это конвейер
Обработка входящего сообщения ДОЛЖНА быть явным конвейером: разбор и доступ, контекст и память,
модель и инструменты, ответ и действия (напоминание, файл, опрос).

#### Scenario: Напоминание через инструмент
- GIVEN пользователь просит напомнить
- WHEN модель вызывает инструмент
- THEN ядро получает результат и отправляет подтверждение
- AND порядок шагов описан в одном месте, а не рассеян по файлу

### Requirement: Команды — отдельный маршрутизатор
Команды `/...` ДОЛЖНЫ разбираться в отдельном маршрутизаторе, а не внутри обработки модели.

#### Scenario: Неизвестная команда
- GIVEN пользователь отправил неизвестную команду
- WHEN маршрутизатор её не нашёл
- THEN в личном чате приходит текст «Неизвестная команда. Список: /help»
- AND в группе бот молчит (сохранённое поведение)

## ADDED Requirements

### Requirement: Режимы в общем модуле
Описания режимов ответа (`/mode`) ДОЛЖНЫ жить в `src/core/modes.mjs`, а не в маршрутизаторе команд.

#### Scenario: Импорт режимов
- GIVEN маршрутизатору команд нужен список режимов
- WHEN он импортирует его
- THEN импорт идёт из `src/core/modes.mjs`
- AND `conversation` берёт режимы оттуда же

#### Scenario: Поведение не изменилось
- GIVEN пользователь меняет режим командой `/mode`
- WHEN команда выполняется
- THEN тексты и поведение прежние
- AND тесты проходят без правок

## ADDED Requirements

### Requirement: Пространства и роли
Пользователь создаёт проект и явно добавляет в него данные; роли MVP — owner, editor, viewer;
по умолчанию проект личный, общий создаётся явно.

#### Scenario: Создание проекта
- GIVEN пользователь в чате
- WHEN просит «создай проект Ремонт»
- THEN проект создан, просящий становится owner
- AND бот подтверждает активный проект краткой строкой

#### Scenario: Viewer не меняет данные
- GIVEN пользователь имеет роль viewer в проекте
- WHEN он просит изменить задачу обычным текстом, через API или callback
- THEN изменение отклоняется с понятным текстом
- AND данные проекта не меняются

### Requirement: Активный проект и область ответа
Активный проект хранится на уровне пользователя и разговора/темы. Ответ на старое сообщение
сохраняет область исходного объекта, даже если текущий проект изменился; при противоречии бот
уточняет назначение.

#### Scenario: Ответ на карточку из старого проекта
- GIVEN текущий проект «Поездка», а карточка относится к «Ремонту»
- WHEN пользователь отвечает на карточку
- THEN изменение применяется к объекту «Ремонта»
- AND при противоречии бот спрашивает, к какому проекту отнести изменение

### Requirement: Доступ, приглашение и отзыв
Приглашение связывается с подтверждённой учётной записью и принимается получателем; пересылка
карточки сама по себе доступа не даёт. Отзыв доступа действует для API, поиска, кеша, скачивания
файлов и ожидающих доставки уведомлений. Уже отправленные сообщения отозвать нельзя — это
ограничение описывается пользователю.

#### Scenario: Отзыв доступа
- GIVEN пользователь был участником проекта
- WHEN owner отзывает доступ
- THEN пользователь не видит проект ни в списке, ни по известному id
- AND он не получает очередное уведомление, результаты поиска или файл проекта

### Requirement: Архив и сводка по проекту
Архивирование прекращает новые фоновые инициативы, сохраняя доступную историю. «Что по проекту?»
возвращает актуальную сводку: незавершённые задачи, сроки, блокировки, последние решения со
ссылками на источники; устаревшая сводка пересчитывается или помечается датой.

#### Scenario: Сводка
- GIVEN в проекте есть задачи, сроки и решения
- WHEN пользователь спрашивает «что по проекту?»
- THEN в сводке незавершённые задачи, сроки, блокировки и решения со ссылками
- AND удалённые и недоступные объекты в сводку не попадают

### Requirement: Миграция в личную область
Существующие данные мигрируют в личную область владельца, а не в общий проект. Миграция
выполняется с резервной копией и флагом; откат кода не должен терять новые записи.

#### Scenario: Первый запуск после обновления
- GIVEN в хранилищах есть записи без scope_id
- WHEN запускается новая версия
- THEN все записи получают личное пространство владельца
- AND копия данных сделана до миграции

## Совместимость и безопасность (из общих условий BP-03)

- Идентичность — только из проверенного контекста транспорта, не из аргументов модели.
- Повтор события или callback не повторяет предметное действие (ключ идемпотентности, версия).
- Конфликт версий обновляет карточку или уточняет, но не перезаписывает молча.
- Личные тексты и токены не попадают в публичные спеки и логи; в тестах — синтетические данные.
- Если зависимость не реализована, допускается интерфейс и тестовый адаптер, но не выдача
  заглушки за работающую интеграцию.
